# Intermanage

Aplikacja do zarządzania sklepem Intermarché. Dane będą pochodzić głównie z plików Excel `.xlsm` i formularzy ręcznych.

## Współpraca

- Odpowiadamy po polsku.
- Rozwijamy projekt małymi krokami: najpierw fundamenty (logowanie, role, użytkownicy), moduły biznesowe (raporty, importy Excel) dopiero na prośbę.
- Funkcje projektujemy pod codzienną pracę supermarketu: sprzedaż, stany magazynowe, zamówienia, pracownicy, straty.
- Skille projektu są w `.claude/skills/` (graphify, impeccable, emil-design-eng i inne Emila Kowalskiego, taste-skill). Przy pracy nad UI korzystamy z impeccable i emil-design-eng.

## Uruchomienie

```bash
docker compose up -d                       # PostgreSQL 17 na localhost:5433 (lokalny Postgres zajmuje 5432)
cd backend && ./mvnw spring-boot:run       # API na :8080, Flyway migruje schemat przy starcie
cd frontend && npm run certs              # raz: certyfikat mkcert dla lvh.me i *.lvh.me (frontend/certs, poza gitem)
cd frontend && npm run dev                 # https://intermanage.lvh.me:5173, proxy /api -> :8080 (bez certyfikatu: http)
cd backend && ./mvnw test                  # testy integracyjne (Testcontainers, wymaga Dockera)
cd backend && ./mvnw -Dbuild.dir=target-cli test   # to samo przy otwartym VS Code: IDE nie nadpisze klas w target/
cd frontend && npm run build && npm run lint
```

Pierwsze konto właściciela tworzy `OwnerBootstrap`, gdy w bazie nie ma żadnego. Login to `OWNER_USERNAME`, hasło `OWNER_PASSWORD` (domyślnie `admin` / `admin`). Pusty `OWNER_PASSWORD` oznacza losowe hasło wypisane raz w logach backendu.

## Architektura

- **backend/**: Spring Boot 4.1, Java 25, Spring Security 7, JPA + Flyway (`src/main/resources/db/migration`), Jackson 3 (`tools.jackson`), MapStruct. Schemat zmieniamy tylko migracjami (`ddl-auto=validate`).
  - Pakiety warstwowe w `com.intermanage.backend`: `controller` (REST), `service` (logika, transakcje), `repository` (`JpaRepository`), `entity` (encje JPA i enumy zapisywane w bazie), `dto` (rekordy request/response), `mapper` (MapStruct), `component` (pozostałe beany: parser raportu, czytnik Excela, mailer, bootstrap), `config`, `security`, `exception`.
  - Encja → DTO tylko przez mappery MapStruct (`@Mapper`, domyślnie bean Springa). Niezmapowane pole DTO to błąd kompilacji (`unmappedTargetPolicy=ERROR`). DTO nie mają statycznych `from()`.
  - Dostęp do bazy przez repozytoria JPA, bez `JdbcTemplate`. Encje zapisywane masowo (produkty) biorą id z sekwencji z `allocationSize = 50`, bo przy `IDENTITY` Hibernate nie grupuje INSERT-ów. `BigDecimal` w encji zawsze z `precision`/`scale` jak w migracji, inaczej Hibernate zaokrągli do 2 miejsc.
- **frontend/**: Vite + React 19 + TS, shadcn/ui (wariant base-nova, czyli **Base UI, nie Radix**: zamiast `asChild` jest `render={<Button />}`, `Select` dostaje `items` do wyświetlania etykiet), Tailwind 4, react-router 7, react-hook-form.
  - **TanStack Query** trzyma wszystkie dane z API (w tym zalogowanego użytkownika: `useMe`). **Redux** służy tylko do stanu UI (`store/uiSlice.ts`) i niewysłanych szkiców (`store/deliOrderDraftSlice.ts`: zamówienie garmażu per sklep + dostawca, zostaje po wyjściu z zakładki i odświeżeniu strony dzięki kopii w localStorage, znika po wysłaniu albo wyczyszczeniu). Danych z serwera nie kopiujemy do Reduxa.
  - `DialogContent` ma szerokość `calc(100% - 2rem)` (klasa `sm:max-w-*` to tylko górny limit) i przewija się, gdy jest wyższe od ekranu. `MultiComboboxField` zostaje otwarty po zaznaczeniu i ma stopkę „Gotowe”.
- Formularze składamy z `components/form` (`Form`, `TextField`, `SelectField`, `MultiComboboxField` (wielokrotny wybór z wyszukiwarką, np. sklepy), `SwitchField`, `SegmentedField`, `FormActions`, `FormNote`). Pola mają pływającą etykietę. `Button` ma `loading` i rozmiar `xl` dla głównej akcji. Nie składamy pól ręcznie z `Input` + `Label`.
  - Od 1280 px i 1600 px rośnie bazowy rem (`index.css`), więc cały interfejs powiększa się proporcjonalnie. Rozmiary podajemy w klasach Tailwinda (rem), nie w px.
  - Ekrany z kilkoma krokami dostają podpowiedź `components/HowTo` (numerowane kroki, można ją schować; schowane podpowiedzi są w `ui.hiddenHints` i w localStorage).
  - Czerwień marki (`bg-brand`, `text-brand`) tylko dla znaku firmowego i aktywnej pozycji w menu, nigdy dla przycisków (czerwony = błąd lub usuwanie).
  - Wszystkie żądania idą przez `lib/api.ts`, który obsługuje CSRF i zamienia ProblemDetail na `ApiError`. Błędy pól mapujemy przez `applyServerErrors`.

## Uwierzytelnianie i uprawnienia

- Bezstanowo: JWT (HS256, `JwtService`) w ciasteczku `AUTH_TOKEN` (HttpOnly, SameSite=Lax), bez sesji HTTP. Do tego CSRF w trybie SPA (`XSRF-TOKEN` → nagłówek `X-XSRF-TOKEN`), bo ciasteczko z tokenem przeglądarka wysyła sama. Bez CORS, bo front i API stoją na jednym originie.
- Klucz podpisu: `JWT_SECRET` (min. 32 znaki). Bez niego klucz losowany jest przy starcie, więc restart backendu wylogowuje wszystkich. Ważność tokenu: `AUTH_TOKEN_TTL` (domyślnie 8h), na HTTPS ustaw `AUTH_COOKIE_SECURE=true`.
- Logowanie: `POST /api/auth/login` (JSON `{username, password}`, ustawia ciasteczko), wylogowanie: `POST /api/auth/logout` (czyści ciasteczko), bieżący użytkownik: `GET /api/auth/me`.
- Rola **Właściciel** jest systemowa (`roles.owner = true`): ma wszystkie uprawnienia, nie da się jej edytować ani usunąć, a w systemie musi zostać co najmniej jeden aktywny właściciel. Pozostałe role tworzy właściciel w Ustawieniach.
- Uprawnienia działają per kategoria narzędzi (`PermissionCategory`) z poziomem `VIEW` lub `EDIT` (EDIT obejmuje VIEW). Authorities Spring Security: `ROLE_OWNER` oraz `KATEGORIA:POZIOM`, np. `SALES:VIEW`.
- `JwtAuthenticationFilter` (własny filtr, celowo nie `oauth2ResourceServer`, bo ten wyłącza CSRF dla żądań z tokenem) przy każdym żądaniu wczytuje użytkownika z tokenu z bazy, więc zmiany ról działają od razu. Token niesie `session_version` (claim `sv`): blokada konta albo zmiana hasła unieważnia wcześniej wydane tokeny.
- `/api/settings/**` jest dostępne tylko dla właściciela.
- Nowych pracowników się zaprasza: właściciel podaje e-mail, konto powstaje bez hasła, a `ActivationService` wysyła jednorazowy link `/aktywacja?token=…` (ważny `ACTIVATION_LINK_TTL`, domyślnie 72h, w bazie tylko SHA-256). Na razie `LoggingAccountMailer` wypisuje maila w logach (`[MAIL] …`). System maili podpinamy jako inną implementację `AccountMailer`.
- `password_change_required`: nowe konto, hasło tymczasowe od właściciela albo domyślne hasło bootstrapu. Taki użytkownik ma tylko authority `PASSWORD_SETUP_REQUIRED` i dostęp wyłącznie do `/api/auth/me` i `POST /api/auth/password/setup`. Frontend przekierowuje go na `/ustaw-haslo`.

### Nowy moduł / kategoria narzędzi

1. Dodaj stałą w `backend/.../entity/PermissionCategory.java`. Nazwa stałej ląduje w bazie, więc istniejących nie zmieniamy.
2. Dodaj ścieżkę i ikonę w `frontend/src/features/tools/categories.ts` (`TOOL_ROUTES`) oraz typ w `lib/types.ts`.
3. Zabezpiecz endpointy: `@PreAuthorize("hasAuthority('SALES:VIEW')")` dla odczytu, `'SALES:EDIT'` dla zmian. We froncie używaj `useCan(category, level)` / `<RequireAuth permission={...}>`.
4. Dane sklepu idą pod `/api/stores/{storeId}/...` i do uprawnienia dokładamy `and @storeAccess.canAccess(authentication, #storeId)`. We froncie bierz sklep z `useCurrentStore()`, a jego id dodawaj do ścieżki i klucza zapytania.

## Sklepy

- Sklep (`stores`) ma numer punktu sprzedaży z systemu Intermarché (np. 10023, ten sam co w nagłówku raportów), nazwę, adres i flagę `active`. Właściciel zarządza nimi w Ustawieniach (`/api/settings/stores`). Sklepów nie usuwamy, tylko wyłączamy.
- Dostęp: właściciel widzi wszystkie sklepy, pracownik tylko przypisane (`user_stores`, pole `storeIds` w formularzu użytkownika) i aktywne. Rola mówi, *co* wolno, przypisanie mówi, *w którym sklepie*. Sprawdza to `security/StoreAccess`.
- Pracownik bez żadnego aktywnego sklepu nie może się zalogować (403 po poprawnym haśle) ani aktywować konta (link nie jest wtedy zużywany). Odebranie ostatniego sklepu kończy jego sesję przy następnym żądaniu (`JwtAuthenticationFilter`). Właściciel loguje się zawsze. W `PUT /api/settings/users/{id}` `storeIds: null` znaczy „bez zmian”.
- `/api/auth/me` zwraca `stores` (dostępne sklepy). Wybrany sklep jest w Reduxie (`ui.currentStoreId`, zapamiętany w localStorage). `useCurrentStore()` wraca do pierwszego sklepu, gdy zapamiętany przestał być dostępny.

## Import raportu produktów

- Pracownik codziennie wgrywa raport z systemu sklepu (np. `BAZA DO STRONY.xlsx`, arkusz Mercalys, ok. 72 tys. pozycji) na `/import` → `POST /api/stores/{storeId}/imports/products` (multipart `file`, `IMPORTS:EDIT`). Historia: `GET` na tę samą ścieżkę (`IMPORTS:VIEW`). Kartoteka, pary EAN i historia są osobne dla każdego sklepu. Numer sklepu z nagłówka raportu („Numer punktu sprzedaży 10023”) musi się zgadzać z wybranym sklepem, inaczej import jest odrzucany.
- `component/XlsxReader` czyta .xlsx/.xlsm strumieniowo (zip + StAX, bez Apache POI). `component/ProductReportParser` szuka kolumn po nazwie z nagłówka (EAN, NAZWA, ITM8...) i sprawdza „Ilość linii” ze stopki. Jeden błędny wiersz odrzuca cały plik (`rowErrors` w ProblemDetail).
- Kluczem produktu jest **ITM8**, nie EAN. Scalanie idzie w jednej transakcji: `ProductImportService` wczytuje całą kartotekę jako encje i porównuje ją z plikiem w pamięci: nowe kody są dodawane, zmienione pola nadpisywane, a produkty, których zabrakło w pliku, zostają (`last_seen_import_id` wskazuje ostatni import, w którym były). Raport starszy niż ostatnio wgrany jest odrzucany.
- **Pary ITM8 + EAN** (`product_eans`) nigdy nie są nadpisywane ani usuwane: ten sam ITM8 bywa przenoszony na nowy EAN, EAN na nowy ITM8, a system sklepu często poprawia błędnie przypisane EAN-y. Sprzedaż i inne dane z raportów podpinamy pod parę, nie pod sam EAN. `products.ean` to tylko bieżący EAN. Zmiany przypisań z każdego importu trafiają do `product_ean_changes` (`GET /api/imports/products/{id}/ean-changes`).
- Kolumna VAT w raporcie to kod stawki z systemu sklepu, a nie procent.

## Zamówienie garmażu

- Kategoria uprawnień `DELI_ORDERS`, front `/zamowienie-garmazu/*` (zakładki-podstrony: Zamów, Wysłane, Przychodzące, Formularz, `zamowienia/:id`), API `/api/stores/{storeId}/deli-order/...`, gdzie `storeId` to sklep, w którym pracuje użytkownik.
- Formularz należy do sklepu-dostawcy: działy (`order_sections`, zakładki) → kategorie (`order_categories`) → produkty z jego kartoteki (`order_category_products`, z jednostką zamawiania `order_unit` KG/SZT). Układa go `DELI_ORDERS:EDIT` po kliknięciu ołówka; każda zmiana zwraca cały formularz. Zmiany idą po kolei (`scope` mutacji), więc pole wyszukiwarki nie blokuje się w trakcie zapisu: Enter dodaje pierwszy wynik, fokus zostaje, a widok przewija się do nowej pozycji. Do kategorii można wkleić listę z Excela (przycisk „Wklej z Excela” albo wklejenie w wyszukiwarkę): kolumna EAN + jednostka (pusta = kg, `kg`/`szt`), `POST .../categories/{id}/products/paste` szuka po bieżącym EAN-ie z kartoteki, znanym pozycjom zmienia jednostkę i zwraca nieznalezione EAN-y. Długie działy mają `CategoryNav`: spis kategorii w prawym dolnym rogu (komputer) i strzałki po lewej (telefon), także w zakładce Zamów.
- Zaproszenia (`deli_form_invitations`): dostawca zaprasza sklepy, zaproszony sklep przyjmuje (EDIT) i wtedy zamawia z formularza dostawcy. Ze swojego formularza sklep zamawia bez zaproszenia. Cofnięcie zaproszenia odcina formularz, złożone zamówienia zostają.
- Zamówienia (`deli_orders`, `deli_order_items`): składa VIEW, z datą dostawy (≥ dziś, strefa Europe/Warsaw) i ilościami (kg do 3 miejsc, sztuki całe). Dział i kategoria są kopiowane tekstem. Dostawca (EDIT) poprawia ilości (`ordered_quantity` zostaje, `quantity` się zmienia) i oznacza jako zrealizowane. Dopóki zamówienie ma status NEW, można je usunąć (`DELETE .../orders/{id}`, zamawiający z VIEW, dostawca z EDIT), ale tylko po swojej stronie: `store_deleted_at` / `form_store_deleted_at` ukrywa je z listy tego sklepu, druga strona widzi status „Usunięte”, a usuniętego po którejkolwiek stronie nie da się poprawiać ani realizować. Przywraca `POST .../orders/{id}/restore` (toast „Przywróć”, banner w szczegółach, później logi). Licznik nowych zamówień i zaproszeń: `GET .../overview`, w menu `DeliNewOrdersBadge`.
- Wyszukiwarka produktów (`GET .../products?query=`, `repository/ProductSearch`): od 3 znaków bez spacji, każde słowo musi pasować w dowolnej kolejności jako fragment nazwy lub marki, początek EAN albo fragment ITM8; max 20 wyników.
- Kalendarz marki: `components/ui/calendar.tsx`, w formularzach `DateField` (`components/form`). Daty bez godziny jako tekst RRRR-MM-DD (`lib/dates.ts`).
- Pozycje spoza formularza: zamawiający wyszukuje produkty w kartotece dostawcy (`GET .../suppliers/{formStoreId}/products`) i wysyła je w `extras` z jednostką i działem (`sectionId`), bo kartka z wydruku trafia do działu. Dopisuje je na dole zakładki działu; w zamówieniu lądują w tym dziale jako kategoria „Spoza formularza”, za pozycjami z formularza. Ilość 0 nie jest wysyłana. Ceny nie są pokazywane w module.
- Zamówienie jedzie do sklepu na **dokumencie ruchu międzymagazynowego** (typ MM z modułu Dokumenty, w sklepie-dostawcy). Dostawca z EDIT przypina go w szczegółach zamówienia (`POST .../orders/{id}/documents` z `documentId`, podpowiedzi: `GET .../orders/{id}/documents/candidates?query=` - bez zapytania dokumenty z tygodnia przed datą dostawy do dwóch dni po). Można przypiąć kilka. Odpięcie (`DELETE .../orders/{id}/documents/{documentId}`) ustawia `deli_order_documents.unlinked_at/by`, wpis zostaje; „Przywróć” to ponowne przypięcie. Zamawiający widzi przypięte dokumenty (bez kwot), a dokument MM w module Dokumenty pokazuje zamówienia, które na nim jadą (`DocumentResponse.deliOrders`).
- Pliki zamówienia (`GET .../orders/{id}/export/{lst|xlsx|pdf}`, `component/DeliOrderDocuments`): `.lst` z EAN-ami (CRLF), Excel (EAN, nazwa, marka, ilość, `component/XlsxWriter` bez POI) i PDF (OpenPDF, font DejaVu z `resources/fonts`). W PDF każdy dział zaczyna się na nowej kartce, z pełnym nagłówkiem, własną numeracją Lp., podpisami i stroną liczoną w obrębie działu, bo kartki trafiają do różnych działów. Kategorie mają nagłówki powtarzane na każdej stronie, kolumny Lp. / Towar / Zamówiono / Zrealizowano (puste, na długopis) / Kod. Kod to EAN-13 lub EAN-8, gdy suma kontrolna się zgadza, inaczej Code 128. Wiersze nie dzielą się między strony. Pozycje z ilością 0 są pomijane.

## Dokumenty

- Kategoria `DOCUMENTS`. Front: `/dokumenty` (kafelki typów), `/dokumenty/:typ` (lista, np. `/dokumenty/pl`), `/dokumenty/:typ/:id` (dokument z liniami). API: `GET /api/stores/{storeId}/documents` (typy z liczbą dokumentów + `lastReportGeneratedAt`), `GET .../documents/{typ}?page=&query=&sort=&direction=` (strona po 100, `DocumentPage` z `hasMore`, `matchingCount` i sumami do „Razem”), `GET .../documents/{typ}/{id}`.
- Typy w `entity/DocumentType.java` (nazwa stałej = kod z raportu, trafia do bazy): PZ przyjęcia towaru, PK korekty błędów sklepu, WZ korekty od dostawcy, PL likwidacje, PPP przeniesienia stanów, ZW zwroty do dostawcy, MM ruchy międzymagazynowe (towar jadący do innego sklepu), RWPO potrzeby sklepu, RWREP reprezentacja. **W interfejsie tylko pełne nazwy (`label`, `singular`), nigdy kody.** Ikony kafelków: `features/documents/document-icons.ts`. Typy spoza listy są przy imporcie pomijane (`document_imports.skipped_types`).
- Wszystkie typy mają te same kolumny, więc są w jednej parze tabel: `documents` (unikalne: sklep + typ + numer, z podsumowaniem linii) i `document_lines` (unikalne: dokument + `N° ligne` + ITM8, bo zwroty prasy mają wszystkie linie z numerem 1). Dostawca jest przy linii; w nagłówku tylko wspólny (w likwidacjach, przeniesieniach, reprezentacji linie mają różnych dostawców → „różni dostawcy”).
- Raport wgrywa się w **Imporcie danych** (`/import`): `POST /api/stores/{storeId}/imports/documents` (`IMPORTS:EDIT`), historia `GET` tamże (`IMPORTS:VIEW`). Import danych to siatka kart raportów (produkty, Wejścia/Wyjścia) i wspólna historia obu na dole.
- Źródło: raport „Statystyka: Wejścia/Wyjścia” z systemu sklepu (.xlsx, np. `Zeszyt2.xlsx`). `component/DocumentReportParser` szuka kolumn po nazwie bez znaków diakrytycznych (`Numéro document interne` → `numero document interne`), bierze numer sklepu z „TRYTOMA Sp. z o.o. - 10023” (musi się zgadzać z wybranym sklepem), okres z „Wybór danych : OD … do …” i sprawdza liczbę linii z „… 6745 linie” (system wlicza do niej wiersz nagłówka). Stopka „Razem:” jest pomijana. Błędna linia zapisywanego typu odrzuca cały plik.
- Raporty obejmują nakładające się okresy: ponowne wgranie aktualizuje nagłówek i linie, nowe linie dopisuje, a brakujących nie usuwa. Numery dokumentów i kody to tekst (zera wiodące, np. `240460000520`). `TVA` to tu stawka w procentach, `0` w „Numéro document fournisseur” oznacza brak.
- **Dokumentów są tysiące:** lista typu przychodzi z serwera stronami po 100 (`useInfiniteQuery`), kolejne strony dociąga `lib/use-load-more.ts`, gdy dojedziesz do końca listy. Wyszukiwanie (`repository/DocumentSearch`: każde słowo jako fragment numeru, dostawcy, jego kodu albo nr dok. dostawcy, bez polskich znaków przez `translate`), sortowanie (klik w nagłówek, `nextSort` z `lib/table-sort.ts`) i sumy „Razem” (`DocumentTotalsRepository`) liczą się w bazie. Domyślnie po numerze rosnąco. W przyjęciu PZ numer dokumentu dostawcy da się poprawić (`PUT|DELETE .../documents/pz/{id}/supplier-document-number`, `DOCUMENTS:EDIT`, `features/documents/SupplierDocumentNumber`): `supplier_document_number` to numer obowiązujący, `report_supplier_document_number` ten z raportu, a poprawka (`supplier_document_number_edited_at/by`) przetrwa kolejne importy. Po zmianie front odświeża faktury KSeF, bo po tym numerze faktura staje się „wprowadzona”. Linie jednego dokumentu sortuje i filtruje przeglądarka (`useTableSort`, `matchesSearch`), też rysując je po 100 przy przewijaniu. Ilości bez jednostki (jednostka z raportu opisuje produkt, waga jest w nazwie). Wgrywanie pliku: `components/FileDropZone`, błędy wierszy: `components/ImportError`.

### Dostawcy i gratisy

- **Lista dostawców** (`suppliers`, per sklep) pochodzi z raportu „Lista dostawców” z systemu sklepu (np. `nananna.xlsx`, arkusz Mercalys: „… - Numer punktu sprzedaży 10023”, „Data : 25/10/2026 12:46:21”, kolumny Kod dost. … Ilość ITM, stopka „Ilość linii: 317”). Wgrywa się ją w Imporcie danych (trzecia karta): `POST /api/stores/{storeId}/imports/suppliers` (`IMPORTS:EDIT`), `GET` tamże zwraca liczbę dostawców i historię. `component/SupplierReportParser`, scalanie w `SupplierService` po **Kod dost.** (ten sam co `supplier_code` w liniach dokumentów): nowi dodawani, znani nadpisywani, brakujący zostają (`last_import_id`), starszy raport odrzucany.
- Dostawcę spoza systemu sklepu dodaje się ręcznie (`POST /api/stores/{storeId}/suppliers`, `DOCUMENTS:EDIT`): bez kodu, jest tylko w aplikacji, nazwa unikalna w sklepie. Lista do wyboru: `GET .../suppliers` (`DOCUMENTS:VIEW`, wszyscy naraz, filtruje przeglądarka).
- **Gratis:** przeniesienie stanów (`DocumentType.canBeGratis()`, tylko PPP) można zarejestrować jako gratis od dostawcy: `PUT .../documents/{typ}/{id}/gratis` z `supplierId` (`DOCUMENTS:EDIT`; ponowne wywołanie zmienia dostawcę, poprzedni wpis dostaje znacznik), `DELETE` cofa (znacznik), `POST .../gratis/restore` przywraca ostatni. Wartością gratisu jest sprzedaż brutto dokumentu (`documents.sale_value_gross`), nie kopia, więc późniejsze importy ją poprawiają. Dokument z linią o nazwie zawierającej „GRATIS” ma `has_gratis_line` (liczone w `Document.recalculateSummary`), a lista pokazuje „Może być gratisem”. W oknie wyboru podpowiadany jest dostawca większości linii (bez pozycji GRATIS, którą wystawia sam sklep).

## Kalkulator cen garmażu

- Kategoria `DELI_PRICES`, front `/kalkulator-garmazu` (lista z wyszukiwarką, na górze „Odśwież ceny” i „Eksport do Excela”), `/kalkulator-garmazu/nowa` i `/kalkulator-garmazu/:id` (kreator), API `/api/stores/{storeId}/price-calculations` (`GET` lista, `/{id}`, `/finished-products`, `/products?query=`, `/export/xlsx`: VIEW; `POST`, `PUT /{id}`, `DELETE /{id}`, `POST /{id}/restore`, `POST /refresh-prices/preview?calculationId=`, `POST /refresh-prices`: EDIT). Usunięcie to znacznik (`deleted_at`), toast „Przywróć”.
- Kalkulacja (`price_calculations`, `price_calculation_items`) jest dla **gotowego wyrobu z kartoteki** (`product_id`, tylko nomenklatury 24, 36, 46: `PriceCalculationService.FINISHED_NOMENCLATURES`, NOM „36 60 02” → dział 36), jeden wyrób = jedna aktywna kalkulacja. Nazwa to kopia nazwy wyrobu. Tryb `PER_KG` (ilości na 1 kg wyrobu) albo `PER_BATCH` (na cały przepis, z `batch_yield` kg wyrobu), składniki z kartoteki z ilością. `PUT` zastępuje listę składników; każdy produkt najwyżej raz.
- **Cena składnika** (`component/IngredientPricing`): z ostatniej dostawy, czyli najnowszej linii przyjęcia PZ z tym ITM8 w sklepie (`DocumentLineRepository.findPricedLines`), a gdy produktu nie było w dostawach, z kartoteki. Cena zakupu w PZ i w kartotece dotyczy sprzedawanej sztuki, a WAGA (`net_content`) mówi, ile w niej jednostki, więc koszt jednostki to cena / `net_content` (`Product.unitCostOf`, np. bita śmietana 55 g za 1,69 zł → 30,73 zł/kg). Ilość wpisuje się w `Product.getCostUnit()`: kg, L, szt.; artykuły wagowe „A.Wa” liczą się na kg.
- **Waga sztuki:** warzywa na sztuki (JED szt., WAGA 1 = 1 sztuka, cena za sztukę) wpisuje się w sztukach. Przy takim składniku kreator ma pole „1 szt. waży ok. … kg” (`products.piece_weight`, z autorem i datą, zapamiętane dla produktu w sklepie, import raportu go nie rusza; przychodzi w `items[].pieceWeight`, `null` czyści). Waga nie zmienia kosztu, tylko wlicza sztuki do **wagi surowców** przepisu. To waga przed obróbką, a nie gotowego wyrobu (z 3 kg surowców wychodzi np. 1 kg), dlatego nie podpowiada wydajności. Przy całym przepisie kreator pokazuje „Wydajność” = wydajność / waga surowców, gdy znane są wagi wszystkich składników.
- **Ceny są zapamiętywane** w składniku (`unit_cost`, `price_source` DELIVERY/CATALOG, `price_document_id`, `priced_at`): nowy składnik dostaje aktualną cenę, przy zapisie znane składniki zachowują swoją. Zmienia je dopiero „Odśwież ceny” (`prices_refreshed_at`).
- **Własna cena** (`manual_price`, z autorem i datą) zastępuje wyliczoną w eksporcie; `salePrice` w odpowiedziach to cena do eksportu, `calculatedPrice` wyliczona. **„Odśwież ceny” ma dwa kroki** (`RefreshPricesButton`): podgląd bez zmian w bazie, potem zatwierdzenie z decyzjami. Pyta (`PriceCalculationService.needsDecision`) o kalkulacje z własną ceną, gdy wyliczona wychodzi inna niż dotąd, i o te z ceną wyliczoną, gdy zmienia się o ≥ 10% (`PRICE_CHANGE_THRESHOLD_PERCENT`); reszta odświeża się bez pytania. `KEEP` zostawia cenę sprzed odświeżenia (wyliczona zostaje zapisana jako własna), `ACCEPT` bierze nową wyliczoną i kasuje własną. Gdy od podglądu doszła kalkulacja wymagająca decyzji, zatwierdzenie zwraca 409.
- **Cena sprzedaży 1 kg** (`PriceCalculation.getSalePrice()`, ten sam wzór w `format.ts` → `salePrice`): koszt 1 kg (przy `PER_KG` suma składników, przy `PER_BATCH` suma / wydajność) × (100 + `MARKUP_PERCENT` = 60)% × (100 + VAT)%, zaokrąglone **w górę** do ,99 zł (15,40 → 15,99; 16,00 → 16,99). VAT na kalkulację: 0, 5, 8 albo 23%, domyślnie 5%. Eksport `.xlsx`: EAN, Nazwa, Cena sprzedaży, VAT %.
- Kreator (`features/deli-prices/CalculationEditor.tsx`) przelicza na bieżąco; wyrób wybiera `FinishedProductPicker` (wszystkie wyroby naraz, filtr po nazwie, marce, EAN), składniki panel po prawej. Niezapisane zmiany pilnuje `useBlocker` i `beforeunload`; „Odśwież ceny” w kreatorze jest wyłączone, dopóki są niezapisane zmiany.

## Faktury KSeF

- Kategoria `KSEF_INVOICES`, front `/faktury-ksef` (lista) i `/faktury-ksef/ustawienia` (tylko EDIT), API `/api/stores/{storeId}/ksef/...`: `GET` (nagłówek: czy połączony, ostatnie pobranie, IDWew sklepu), `GET /invoices` (VIEW, strony po 100), `PUT|DELETE /invoices/{id}/entered`, `POST /sync` (202, zleca pobieranie w tle i zwraca nagłówek), `/settings/**` (EDIT), `GET /invoices/{id}/xml` (VIEW, oryginał prosto z KSeF), `GET /invoices/{id}/pdf` (VIEW, PDF do czytania i wydruku).
- **XML faktury** pobieramy z KSeF tylko raz, przy pierwszym „Pobierz PDF/XML”, i zapisujemy w `ksef_invoice_xml` (faktura w KSeF się nie zmienia, a pobieranie pojedynczych faktur ma limit 64 na godzinę). **PDF faktury** powstaje przy każdym pobraniu z tego XML: `component/KsefInvoiceReader` czyta FA(3) (i FA(2)) po nazwach elementów bez przestrzeni nazw, kody zamienia na polskie opisy i pomija puste sekcje (bez DTD, ochrona przed XXE). `component/KsefInvoicePdf` (OpenPDF, fonty z `PdfFonts`) rysuje nagłówek z numerem KSeF i kodem QR weryfikacji (KOD I: `https://qr.ksef.mf.gov.pl/invoice/{NIP sprzedawcy}/{DD-MM-RRRR}/{SHA-256 pliku, Base64URL}`, host z `app.ksef.base-url`: api → qr, api-test → qr-test; QR rysuje zxing), strony (z Podmiotami 3, np. odbiorca z IDWew), korektę, pozycje (kolumny tylko dla danych z pliku, wiersze „przed korektą”), sumy według stawek, adnotacje, płatność, rozliczenie, warunki transakcji, zamówienie (zaliczki), załącznik i stopkę. Tytuł sekcji jest wierszem nagłówka jej tabeli, więc nie zostaje sam na dole strony. Plik, którego nie da się odczytać, daje 400.
- **Faktury są wspólne dla firmy (NIP), nie dla sklepu** (V20): `ksef_invoices.nip` (unikalne: NIP + numer KSeF), kursor i wynik pobierania w `ksef_sync_states` (per NIP), token KSeF w `KsefSessionService` też per NIP. Pobieranie idzie raz na NIP, a każdy sklep z połączeniem tej firmy od razu widzi jej faktury (według swoich IDWew). Przy sklepie zostaje to, co jego: połączenie (certyfikat), IDWew, pomijani dostawcy, PZ-ki i ręczne „wprowadzona” (`ksef_invoice_entries`, cofnięcie usuwa wpis).
- **Połączenie per sklep** (`ksef_connections`, kontekstem jest NIP firmy): osoba z EDIT wgrywa certyfikat KSeF do uwierzytelniania (.crt) i klucz (.key, PKCS#8 zaszyfrowany hasłem: PBES2/AES-256, odczytuje go sama Java w `component/KsefCredentials`), wpisuje hasło i NIP firmy (kontekst logowania, z sumą kontrolną). Klucz zostaje w bazie tak, jak przyszedł, hasło jest szyfrowane AES-GCM kluczem `APP_SECRET_KEY` (`component/SecretCipher`, 32 bajty w Base64, musi być stały). Bez tego klucza połączenia nie da się zapisać. Po zapisie od razu jest test logowania. Hasło nigdy nie wraca do przeglądarki. Gdy firma jest już połączona w innym sklepie, do którego użytkownik ma dostęp (`companies` w ustawieniach: tylko sklepy z `StoreAccess`, firmy z cudzych sklepów są niewidoczne), osoba z EDIT podłącza sklep bez certyfikatu: `POST .../settings/connection/link` z `{nip}` kopiuje dane logowania (`KsefConnection.copyCredentials`) ze sklepu, do którego ma dostęp, i testuje logowanie. Jeden użytkownik może mieć sklepy kilku firm. W drugą stronę: połączony sklep podłącza naraz inne sklepy użytkownika do swojej firmy (karta „Inne sklepy tej firmy”, `POST .../settings/connection/share` z `{storeIds}`, EDIT, lista w `otherStores` ustawień): kopiuje dane logowania i wynik ostatniego testu bez osobnego logowania do KSeF, pomija sklepy już połączone z tą firmą, a sklep połączony z inną firmą daje 409.
- **Logowanie do KSeF 2.0** (`component/KsefClient`, `app.ksef.base-url`, domyślnie produkcja `https://api.ksef.mf.gov.pl/v2`): `/auth/challenge`, `AuthTokenRequest` (`http://ksef.mf.gov.pl/auth/token/2.0`, `certificateSubject`) podpisany XAdES-BES otaczającym (`component/KsefXadesSigner`, ECDSA-SHA256 dla klucza EC z KSeF, exc-c14n, `SigningTime` + `SigningCertificate`), `/auth/xades-signature`, czekanie na status 200, `/auth/token/redeem`. Token dostępu trzyma w pamięci `KsefSessionService`, dopóki jest ważny. Sprawdzone na środowisku testowym KSeF.
- **Pobieranie** (`KsefSyncService`): faktury zakupowe (`Subject2`), przyrostowo po dacie trwałego zapisu (`PermanentStorage`, `Asc`, `restrictToPermanentStorageHwmDate`), od `ksef_sync_states.sync_cursor` firmy, a za pierwszym razem od `app.ksef.sync-from` (2026-02-01). Okna mają do 90 dni (KSeF przyjmuje najwyżej 100), strony po 250, scalanie po numerze KSeF. Kolejna strona zaczyna się od daty trwałego zapisu ostatniej faktury (nie przez `pageOffset`, bo głębokie strony KSeF liczy coraz dłużej), a brak odpowiedzi albo 5xx (`KsefException.temporary()`) jest powtarzany do 3 razy; timeout odczytu 120 s. KSeF pozwala tylko na 16 zapytań o metadane na minutę i 20 na godzinę. Przy 429 postęp zostaje w kursorze, a komunikat mówi, kiedy ruszy reszta. Przycisk „Pobierz z KSeF” pobiera w tle (wirtualny wątek, jedno pobieranie na NIP naraz, wspólne dla sklepów firmy i harmonogramu, połączeniem sklepu, który kliknął): nagłówek (`GET`) ma `syncRunning`, `syncStartedAt` i `syncNewInvoices`, front odpytuje go co 3 s, odświeża listę, gdy przybywa faktur, i po końcu pokazuje wynik. Co `app.ksef.sync-interval` (30 min) pobieranie rusza samo raz dla każdej firmy (połączeniem z udanym testem) (`app.ksef.sync-enabled`, w testach wyłączone w `src/test/resources/config/application.properties`).
- **Limity KSeF** (produkcja, na parę NIP + IP, okna przesuwne): metadane 8/s, 16/min, 20/h; pobranie faktury 8/s, 16/min, 64/h; reszta 10/s, 30/min, 120/h. Przekroczenia KSeF karze coraz dłuższymi blokadami, więc każde zapytanie idzie przez `component/KsefRateLimiter` z zapasem (metadane 2/s, 10/min, 16/h; faktura 2/s, 10/min, 50/h; logowanie 1/s, 4/min, 15/h), liczonym po NIP-ie (sklepy jednej firmy dzielą limit). Krótkie okna przeczekuje (do ~1 min), wyczerpana godzina albo 429 z KSeF (blokada na cały NIP do końca `Retry-After`) kończy zapytanie od razu z czasem „spróbuj za … min”. Historia zapytań i blokad jest też w bazie (`ksef_api_calls`, `ksef_api_blocks`, `component/KsefRateHistory`, wpisy starsze niż 2 h są czyszczone): restart przy wdrożeniu jej nie zeruje, bo KSeF liczy zapytania dalej, a przekroczenie po restarcie kończyło się coraz dłuższymi blokadami. Godzina limitu metadanych to 16 stron po 250, czyli ok. 4 tys. faktur; większa zaległość schodzi w kolejnych pobraniach (co 30 min). W testach wyłączony (`app.ksef.rate-limit-enabled=false`), sprawdza go `KsefRateLimiterTests`.
- **Które faktury widzi sklep:** sklep bez IDWew - wszystkie faktury firmy. Sklep z IDWew (`ksef_internal_ids`, IDWew = NIP firmy + `-` + 5 cyfr, z Podmiotu 3 faktury, `ksef_invoice_internal_ids`) - ze swoimi IDWew i wszystkie bez IDWew, a filtr `internalId` zawęża: `OWN` (tylko z IDWew sklepu), konkretny IDWew, `NONE` (tylko bez IDWew). Faktury z cudzym IDWew są wtedy niewidoczne, także po id (`KsefInvoiceSearch.visibleInStore`). Ustawienia podpowiadają IDWew z pobranych faktur.
- **Pomijani dostawcy** (`ksef_skipped_suppliers`, po NIP): ich faktury znikają z listy, widać je po włączeniu „Pokaż pominiętych dostawców”. Dodaje się ich też z menu faktury.
- **Wprowadzona:** numer faktury równy (bez względu na wielkość liter) numerowi dokumentu dostawcy w przyjęciu PZ sklepu (`DocumentRepository.findDeliveriesBySupplierDocument`, w filtrze podzapytanie w `KsefInvoiceSearch`) albo ręczne oznaczenie w sklepie (`ksef_invoice_entries`, da się cofnąć). Filtry listy: tekst (numer, dostawca, NIP, nr KSeF), daty wystawienia, status, rodzaj (faktury/korekty), IDWew albo „bez IDWew”, pominięci. Sortowanie i sumy netto/brutto liczą się w bazie.
- Pliki certyfikatów (`*.crt`, `*.key`) są w `backend/.gitignore`. Testowy certyfikat z kluczem (hasło `haslo-testowe`) leży w `src/test/resources/ksef/`.

## Konwencje

- **Aktualność danych z raportów:** każdy import zapisuje datę wygenerowania raportu (`report_generated_at`). Raport jest aktualny tylko w dniu wygenerowania; inaczej pokazujemy „Nieaktualne · wymaga wgrania” (`components/ReportFreshness`, `lib/report-freshness.ts`).
- **Nic w aplikacji nie jest usuwane bezpowrotnie.** Usuwanie to znacznik (kiedy, kto), który da się cofnąć: toast z „Przywróć” od razu, a później z logów. Nowe funkcje projektujemy od razu tak; `repository.delete(...)` tylko dla danych technicznych (np. zużyte tokeny aktywacji).

- Komunikaty dla użytkownika (walidacja, błędy, UI) piszemy po polsku, kod i identyfikatory po angielsku.
- Ścieżki we froncie po polsku (`/ustawienia/role`, `/sprzedaz`), API po angielsku (`/api/settings/roles`).
