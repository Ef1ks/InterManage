# Intermanage

Aplikacja do zarządzania sklepem Intermarché. Dane będą pochodzić głównie z plików Excel `.xlsm` i formularzy ręcznych.

## Współpraca

- Odpowiadamy po polsku.
- Rozwijamy projekt małymi krokami: najpierw fundamenty (logowanie, role, użytkownicy), moduły biznesowe (raporty, importy Excel) dopiero na prośbę.
- Funkcje projektujemy pod codzienną pracę supermarketu: sprzedaż, stany magazynowe, zamówienia, pracownicy, straty.
- Skille projektu są w `.claude/skills/` (graphify, impeccable, emil-design-eng i inne Emila Kowalskiego, w tym apple-design, taste-skill). Przy pracy nad UI korzystamy z impeccable, emil-design-eng i apple-design.

## Uruchomienie

```bash
docker compose up -d                       # PostgreSQL 17 na localhost:5433 (lokalny Postgres zajmuje 5432)
cd backend && ./mvnw spring-boot:run       # API na :8080, Flyway migruje schemat przy starcie
cd frontend && npm run certs              # raz: certyfikat mkcert dla lvh.me i *.lvh.me (frontend/certs, poza gitem)
cd frontend && npm run dev                 # https://intermanage.lvh.me:5173, proxy /api -> :8080 (bez certyfikatu: http)
cd backend && ./mvnw test                  # testy integracyjne (Testcontainers, wymaga Dockera)
cd backend && ./mvnw -Dbuild.dir=target-cli test   # to samo przy otwartym VS Code: IDE nie nadpisze klas w target/
cd frontend && npm run build && npm run lint
cd frontend && npm run format -- src/sciezka/Plik.tsx   # Prettier (frontend/.prettierrc.json), tylko zmienione pliki
```

Prettier formatuje tylko pliki, które zmieniamy, nigdy całego `src` naraz (stary kod ma długie linie klas, pełne formatowanie dałoby ogromny diff).

**Dane do sprawdzania:** pytania o dane (czego brakuje, co jest w bazie) sprawdzamy w bazie z `backend/.env` (`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`), nie w lokalnym Dockerze. To baza produkcyjna (`intermanage_prod` na 192.168.33.110), więc tylko zapytania do odczytu (`select`, najlepiej w `begin read only`), bez zmian danych i bez uruchamiania na niej migracji. Przykład: `docker exec -e PGPASSWORD=… intermanage-postgres psql -h 192.168.33.110 -U intermanage_prod -d intermanage_prod -c "…"`.

Pierwsze konto właściciela tworzy `OwnerBootstrap`, gdy w bazie nie ma żadnego. Login to `OWNER_USERNAME`, hasło `OWNER_PASSWORD` (domyślnie `admin` / `admin`). Pusty `OWNER_PASSWORD` oznacza losowe hasło wypisane raz w logach backendu.

## Wdrożenie

- Produkcja: **https://intermanage.pl**, kontener LXC w Proxmoxie (192.168.33.113). Każdy push na `main` uruchamia `.github/workflows/deploy.yml`: testy backendu, build i lint frontu, obrazy `ghcr.io/ef1ks/intermanage-backend` i `-frontend` (tag = sha commita i `latest`), potem Tailscale (subnet router na hoście Proxmox `pve`, `--accept-routes`) + SSH na 192.168.33.113 i `docker compose pull && up -d` w `/opt/intermanage`. **Commit na main to wdrożenie.**
- Stos: `deploy/docker-compose.yml` (backend, `web` = nginx z buildem frontu i proxy `/api`, cloudflared). PostgreSQL stoi w osobnym LXC (192.168.33.110), produkcja ma własną bazę `intermanage_prod` (lokalna praca nie może jej migrować), połączenie (`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`) jest w `.env`. Ruch z internetu idzie przez Cloudflare Tunnel, więc HTTPS kończy się w Cloudflare, a nginx podaje backendowi `X-Forwarded-Proto: https`. Sekrety w `/opt/intermanage/.env` (wzór `deploy/.env.example`). Przygotowanie serwera i sekrety GitHuba: `deploy/README.md`.
- Dockerfile: `backend/Dockerfile` (Maven → JRE 25) i `frontend/Dockerfile` (Vite → nginx, `frontend/nginx.conf`). `backend/.dockerignore` wpuszcza tylko `pom.xml` i `src/main`, żeby klucze KSeF i raporty z dysku nie trafiły do obrazu.

## Architektura

- **backend/**: Spring Boot 4.1, Java 25, Spring Security 7, JPA + Flyway (`src/main/resources/db/migration`), Jackson 3 (`tools.jackson`), MapStruct. Schemat zmieniamy tylko migracjami (`ddl-auto=validate`).
  - Pakiety według modułów, w każdym te same warstwy: `com.intermanage.backend.<moduł>.<warstwa>`. Moduły: `auth` (logowanie, użytkownicy, role, uprawnienia, aktywacja; tu też `security` i `config/SecurityConfig`), `store` (sklepy i sklepy zaprzyjaźnione), `product` (kartoteka, jej import i multikody), `document` (dokumenty, korekty, gratisy, raport przyjęć, powiązania z fakturami KSeF), `supplier`, `nomenclature`, `sales`, `deliorder` (zamówienie garmażu), `deliprice` (kalkulator cen garmażu), `deliproduction` (karty produkcji garmażu), `pricecheck` (raport zakupu bazowego poza bazą), `promotion` (lista promocji), `dataentry` (wprowadzanie nowych artykułów z faktur, propozycje AI), `ksef`, `mail` (kolejka i wysyłka maili dla wszystkich modułów), `meat` (zakup mięsa z dokumentów WZ), `backup` (kopia zapasowa bazy na Dysk Google), `basedelivery` (dostawa z bazy i kody MEA), `importguide` (instrukcje do raportów w Imporcie danych), `common` (wspólne: `exception`, `config/SchedulingConfig`, `component`: `XlsxReader`, `XlsxWriter`, `XlsReader` (stary .xls, BIFF8 w kontenerze OLE, bez POI), `XlsWriter`, `PdfFonts`, `PdfCells` (napisy z PDF-ów z pozycjami), `PdfBarcodes` (EAN / Code 128 na wydrukach), `SecretCipher`, `ReportText` do nagłówków raportów, `Nip`). Warstwy: `controller` (REST), `service` (logika, transakcje), `repository` (`JpaRepository`), `entity` (encje JPA i enumy zapisywane w bazie), `dto` (rekordy request/response), `mapper` (MapStruct), `component` (pozostałe beany: parsery raportów, PDF, klient KSeF, mailer, bootstrap). Ścieżki typu `component/X` niżej są względne do modułu. Kod używany przez kilka modułów idzie do `common`, nie do modułu, który akurat go ma; moduł może korzystać z publicznych klas innego (np. `document` z `ksef`), ale nie z ich metod pakietowych. Testy są w pakiecie głównym.
  - Encja → DTO tylko przez mappery MapStruct (`@Mapper`, domyślnie bean Springa). Niezmapowane pole DTO to błąd kompilacji (`unmappedTargetPolicy=ERROR`). DTO nie mają statycznych `from()`.
  - Dostęp do bazy przez repozytoria JPA, bez `JdbcTemplate`. Encje zapisywane masowo (produkty) biorą id z sekwencji z `allocationSize = 50`, bo przy `IDENTITY` Hibernate nie grupuje INSERT-ów. `BigDecimal` w encji zawsze z `precision`/`scale` jak w migracji, inaczej Hibernate zaokrągli do 2 miejsc.
- **frontend/**: Vite + React 19 + TS, shadcn/ui (wariant base-nova, czyli **Base UI, nie Radix**: zamiast `asChild` jest `render={<Button />}`, `Select` dostaje `items` do wyświetlania etykiet), Tailwind 4, react-router 7, react-hook-form.
  - **TanStack Query** trzyma wszystkie dane z API (w tym zalogowanego użytkownika: `useMe`). Po każdej udanej mutacji `MutationCache` w `lib/query-client.ts` unieważnia wszystkie zapytania (te na ekranie pobierają się od razu), bo zmiana jednego modułu często zmienia inne i inne sklepy. Wyłącza to `meta: { invalidates: false }`: pobieranie plików, podgląd bez zapisu i mutacje, które same podmieniają swoje dane (szybkie zmiany formularza garmażu; wtedy hook sam unieważnia to, co trzeba). **Redux** służy tylko do stanu UI (`store/uiSlice.ts`) i niewysłanych szkiców (`store/deliOrderDraftSlice.ts`: zamówienie garmażu per sklep + dostawca, zostaje po wyjściu z zakładki i odświeżeniu strony dzięki kopii w localStorage, znika po wysłaniu albo wyczyszczeniu). Danych z serwera nie kopiujemy do Reduxa.
  - `DialogContent` ma szerokość `calc(100% - 2rem)` (klasa `sm:max-w-*` to tylko górny limit) i przewija się, gdy jest wyższe od ekranu. `MultiComboboxField` zostaje otwarty po zaznaczeniu i ma stopkę „Gotowe”.
- Formularze składamy z `components/form` (`Form`, `TextField`, `SelectField`, `MultiComboboxField` (wielokrotny wybór z wyszukiwarką, np. sklepy), `SwitchField`, `SegmentedField`, `FormActions`, `FormNote`). Pola mają pływającą etykietę. `Button` ma `loading` i rozmiar `xl` dla głównej akcji. Nie składamy pól ręcznie z `Input` + `Label`.
  - Od 1280 px i 1600 px rośnie bazowy rem (`index.css`), więc cały interfejs powiększa się proporcjonalnie. Rozmiary podajemy w klasach Tailwinda (rem), nie w px.
  - **Menu** (`components/layout/navigation.tsx`, `GROUPS`): menu boczne ma tylko główne kategorie (Zakupy i dokumenty `/zakupy`, Sprzedaż i raporty, Garmaż `/garmaz`, Magazyn i dane `/dane`, Sklep `/sklep`: Pracownicy i grafik oraz Sklepy, Ustawienia `/ustawienia`), z licznikami swoich narzędzi. Kategoria prowadzi na swoją stronę z kafelkami narzędzi (`features/tools/NavGroupPage`), a kategoria z jednym dostępnym narzędziem prosto do niego. W kategorii nagłówek aplikacji pokazuje jej narzędzia jak zakładki (`GroupTabs` w `AppLayout`, stała wysokość nagłówka, nadmiar przewija się w bok). Narzędzie strony to najdłuższa pasująca ścieżka (`locate`), więc `/sprzedaz/koszty-garmazu` należy do Garmażu.
  - Ekrany z kilkoma krokami dostają podpowiedź `components/HowTo` (numerowane kroki, można ją schować; schowane podpowiedzi są w `ui.hiddenHints` i w localStorage).
  - **Ciemny motyw** (`next-themes`, klasa `.dark` na `<html>`, domyślnie jak w systemie, wybór w menu użytkownika: Jasny / Ciemny / Jak w systemie, `lib/theme.ts`, klucz `intermanage.theme` w localStorage; skrypt w `index.html` ustawia klasę przed pierwszym malowaniem). Zmiana przenika przez View Transitions (220 ms, bez przy ograniczonym ruchu). Kolory bierzemy z tokenów (`bg-card`, `bg-muted`, `text-muted-foreground`…), a kolor z palety Tailwinda (np. `bg-amber-100 text-amber-950`) zawsze z wariantem `dark:` (np. `dark:bg-amber-950/60 dark:text-amber-100`). W ciemnym głębię daje jaśniejsza warstwa: `background` (menu, nagłówek) < `card` < `popover` (okna, listy). Pola pisane ręcznie z `border-input bg-background` dostają `dark:bg-input/30` jak `Input`. Logo `hero.webp` ma w ciemnym filtr odwracający jasność.
  - Czerwień marki (`bg-brand`, `text-brand`) tylko dla znaku firmowego i aktywnej pozycji w menu, nigdy dla przycisków (czerwony = błąd lub usuwanie).
  - **Zapis do wybranego folderu** (`lib/saved-folders.ts`, `components/SavedFolder`): File System Access API (Chrome, Edge), uchwyt folderu w IndexedDB pod kluczem rodzaju pliku (`SavedFolderSpec`: `key`, `label`, `suggestedPath`), więc każdy rodzaj ma swój folder wybrany raz. Ścieżki nie da się podać z kodu: `suggestedPath` (np. `N:\avisoconfig`, folder za skrótem na zablokowanym dysku) idzie do schowka, a użytkownik wkleja ją w pasek adresu okna wyboru. `ensureFolderAccess` woła się od razu po kliknięciu (okno zgody wymaga gestu), dopiero potem żądania do API i `saveApiFileToFolder`.
  - **Powrót i przewinięcie:** link „wstecz” u góry podstrony to `components/BackLink` (`to` = strona nadrzędna). Gdy poprzedni ekran był w aplikacji (`lib/history-trail.ts`: ścieżki według `history.state.idx`, zapisuje je `AppLayout`), cofa historię, więc z bonu otwartego z faktur KSeF wraca do faktur (etykieta „Wstecz”, gdy to inny ekran niż `to`); bez historii prowadzi do `to`. `AppLayout` ma `ScrollRestoration` z kluczem = ścieżka: powrót wraca w to samo miejsce strony, a zmiana parametrów adresu na tej samej ścieżce nie przerzuca na górę.
  - Wszystkie żądania idą przez `lib/api.ts`, który obsługuje CSRF i zamienia ProblemDetail na `ApiError`. Błędy pól mapujemy przez `applyServerErrors`.

## Uwierzytelnianie i uprawnienia

- Bezstanowo: JWT (HS256, `JwtService`) w ciasteczku `AUTH_TOKEN` (HttpOnly, SameSite=Lax), bez sesji HTTP. Do tego CSRF w trybie SPA (`XSRF-TOKEN` → nagłówek `X-XSRF-TOKEN`), bo ciasteczko z tokenem przeglądarka wysyła sama. Bez CORS, bo front i API stoją na jednym originie.
- Klucz podpisu: `JWT_SECRET` (min. 32 znaki). Bez niego klucz losowany jest przy starcie, więc restart backendu wylogowuje wszystkich. Ważność tokenu: `AUTH_TOKEN_TTL` (domyślnie 8h, ciasteczko sesyjne, znika po zamknięciu przeglądarki), a z „Nie wylogowuj mnie” przy logowaniu (`rememberMe`, claim `rm`) `AUTH_REMEMBER_ME_TTL` (domyślnie 30 dni, trwałe ciasteczko). Token starszy niż `AUTH_TOKEN_REFRESH_AFTER` (15 min) `JwtAuthenticationFilter` wymienia przy żądaniu na nowy z tym samym `rm` (poza wylogowaniem), więc wygasa dopiero po takiej przerwie w korzystaniu; zmiana hasła zachowuje `rm`. Na HTTPS ustaw `AUTH_COOKIE_SECURE=true`.
- Logowanie: `POST /api/auth/login` (JSON `{username, password}`, ustawia ciasteczko), wylogowanie: `POST /api/auth/logout` (czyści ciasteczko), bieżący użytkownik: `GET /api/auth/me`.
- Rola **Właściciel** jest systemowa (`roles.owner = true`): ma wszystkie uprawnienia, nie da się jej edytować ani usunąć, a w systemie musi zostać co najmniej jeden aktywny właściciel. Pozostałe role tworzy właściciel w Ustawieniach.
- Uprawnienia działają per kategoria narzędzi (`PermissionCategory`) z poziomem `VIEW` lub `EDIT` (EDIT obejmuje VIEW). Authorities Spring Security: `ROLE_OWNER` oraz `KATEGORIA:POZIOM`, np. `SALES:VIEW`.
- `JwtAuthenticationFilter` (własny filtr, celowo nie `oauth2ResourceServer`, bo ten wyłącza CSRF dla żądań z tokenem) przy każdym żądaniu wczytuje użytkownika z tokenu z bazy, więc zmiany ról działają od razu. Token niesie `session_version` (claim `sv`): blokada konta albo zmiana hasła unieważnia wcześniej wydane tokeny.
- `/api/settings/**` jest dostępne tylko dla właściciela.
- Nowych pracowników się zaprasza: właściciel podaje e-mail, konto powstaje bez hasła, a `ActivationService` wysyła jednorazowy link `/aktywacja?token=…` (ważny `ACTIVATION_LINK_TTL`, domyślnie 72h, w bazie tylko SHA-256). Link wysyła mailem `EmailAccountMailer` (implementacja `AccountMailer`, w testach podmieniana przez `RecordingAccountMailer`).
- `password_change_required`: nowe konto, hasło tymczasowe od właściciela albo domyślne hasło bootstrapu. Taki użytkownik ma tylko authority `PASSWORD_SETUP_REQUIRED` i dostęp wyłącznie do `/api/auth/me` i `POST /api/auth/password/setup`. Frontend przekierowuje go na `/ustaw-haslo`.

### Nowy moduł / kategoria narzędzi

1. Dodaj stałą w `backend/.../entity/PermissionCategory.java`. Nazwa stałej ląduje w bazie, więc istniejących nie zmieniamy.
2. Dodaj ścieżkę i ikonę w `frontend/src/features/tools/categories.ts` (`TOOL_ROUTES`) oraz typ w `lib/types.ts`, a narzędzie przypisz do grupy menu w `components/layout/navigation.tsx` (`GROUPS`).
3. Zabezpiecz endpointy: `@PreAuthorize("hasAuthority('SALES:VIEW')")` dla odczytu, `'SALES:EDIT'` dla zmian. We froncie używaj `useCan(category, level)` / `<RequireAuth permission={...}>`.
4. Dane sklepu idą pod `/api/stores/{storeId}/...` i do uprawnienia dokładamy `and @storeAccess.canAccess(authentication, #storeId)`. We froncie bierz sklep z `useCurrentStore()`, a jego id dodawaj do ścieżki i klucza zapytania.

## Maile

- Moduł `mail`. Każdy moduł wysyła przez `MailService.queue(kind, email, name, subject, MailContent)`: mail trafia do tabeli `outgoing_mails` (V36) w bieżącej transakcji, więc wycofana zmiana niczego nie wysyła, a wychodzi w tle po zatwierdzeniu (`MailDispatcher.wakeUp`, wirtualny wątek). Błąd serwera pocztowego nie psuje żądania: zaległe i nieudane wysyła `MailDispatcher.sendDue` co `app.mail.retry-interval`, z odstępami `app.mail.retry-delays` (1 min … 6 h), po ostatnim mail jest porzucany (`failed_at`, `last_error`). Wiersze zostają jako historia.
- Treść: `component/MailContent`, bloki `heading` / `paragraph` / `button` (z adresem pod spodem) / `details` / `note`. Z nich powstaje wersja HTML (wspólny układ, inline style, przycisk ciemny, nie czerwony) i tekstowa. Nowy rodzaj maila = stała w `entity/MailKind` (nazwa trafia do bazy) i kolejność bloków w module, który go wysyła (wzór: `auth/component/EmailAccountMailer`).
- `MailKind.isSecret()` (np. link aktywacyjny): po wysłaniu albo porzuceniu treść w bazie jest zastępowana opisem, żeby nie trzymać działającego linku (w bazie aktywacji jest tylko SHA-256).
- Wysyłka (`config/MailConfig`): SMTP (`spring.mail.*`, STARTTLS na 587) przez relay Brevo, gdy jest `MAIL_HOST`; bez niego `LoggingMailTransport` wypisuje maile w logach (`[MAIL] …`), lokalnie i w testach. Nadawca `MAIL_FROM_ADDRESS` / `MAIL_FROM_NAME` (domena zweryfikowana w Brevo: DKIM, SPF, DMARC), odpowiedzi na `MAIL_REPLY_TO`. Dostawcę zmienia się samymi zmiennymi (`deploy/.env.example`).

## Kopia zapasowa

- Moduł `backup`, front `/ustawienia/kopia-zapasowa` (`features/settings/BackupPage.tsx`, tylko właściciel), API `/api/settings/backup` (V60: `backup_settings` jeden wiersz, `backup_runs` historia). Kopia całej bazy: `component/PgDumpDatabaseDumper` puszcza `pg_dump --format=custom` przez `gpg --symmetric` (AES-256, hasło z ustawień) prosto do pliku w `app.backup.work-dir`, `component/GoogleDriveClient` (REST na `java.net.http`, plik idzie strumieniem) wysyła go uploadem wznawialnym do folderu „Intermanage - kopie zapasowe”, potem kopie ponad `keep_count` (tylko z bieżącego konta) idą do kosza Dysku (`trashed_at`). Obraz backendu ma `postgresql-client-18` (PGDG) i `gnupg`: pg_dump nie może być starszy niż serwer (produkcja: PostgreSQL 18). Odtworzenie: `deploy/README.md`, sekcja 4a.
- **Google OAuth** (konto Gmail właściciela, zakres `drive.file`: aplikacja widzi tylko swoje pliki): `POST .../google/authorize` zapisuje jednorazowy `oauth_state` (10 min) i zwraca adres zgody (`access_type=offline`, `prompt=consent`), front przekierowuje całą stronę. Google wraca na `GET .../google/callback` (`<FRONTEND_URL>/api/settings/backup/google/callback`, nawigacja, więc ciasteczko SameSite=Lax idzie), backend wymienia kod na refresh token i przekierowuje na stronę z `?google=polaczono|blad&komunikat=`. `DELETE .../google` odłącza (cofnięcie tokenu w Google, kopie wyłączone, historia zostaje). Klient OAuth: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`; bez nich `googleConfigured: false`.
- Hasło szyfrowania (min. 12 znaków, `PUT` z `{enabled, runHour, keepCount, password}`, puste = bez zmian) i refresh token są zaszyfrowane `SecretCipher`; hasło nie wraca do przeglądarki. Włączenie wymaga połączenia i hasła (400).
- **Harmonogram** (`BackupRunner.runScheduled`, co `app.backup.check-interval`, `app.backup.schedule-enabled`, domyślnie wyłączone, włącza je tylko `deploy/docker-compose.yml` (`BACKUP_SCHEDULE_ENABLED`), bo lokalny backend z produkcyjnym `.env` robiłby kopie bez pg_dump): automatyczna kopia po `run_hour` (Europe/Warsaw), raz dziennie; nieudana ponawia się po godzinie, najwyżej 3 próby dziennie. `POST .../runs` (202) = „Zrób kopię teraz”. Najwyżej jedna kopia naraz (wirtualny wątek, drugi start = 409), front odpytuje `GET` co 3 s, gdy `running`. Próby „w trakcie” po restarcie dostają FAILED (tylko backend z włączonym harmonogramem). Nieudana kopia: `error` w historii i mail `MailKind.BACKUP_FAILED` do aktywnych właścicieli z e-mailem. W testach `DatabaseDumper` i `GoogleDriveClient` są podmieniane (`BackupIntegrationTests`).

## Sklepy

- Sklep (`stores`) ma numer punktu sprzedaży z systemu Intermarché (np. 10023, ten sam co w nagłówku raportów), nazwę, adres, NIP firmy (opcjonalny, z sumą kontrolną, V22: uzupełniony z połączeń KSeF) i flagę `active`. Po NIP-ie KSeF wie, które sklepy należą do jednej firmy. Właściciel zarządza nimi w Ustawieniach (`/api/settings/stores`). Sklepów nie usuwamy, tylko wyłączamy.
- Dostęp: właściciel widzi wszystkie sklepy, pracownik tylko przypisane (`user_stores`, pole `storeIds` w formularzu użytkownika) i aktywne. Rola mówi, *co* wolno, przypisanie mówi, *w którym sklepie*. Sprawdza to `security/StoreAccess`.
- Pracownik bez żadnego aktywnego sklepu nie może się zalogować (403 po poprawnym haśle) ani aktywować konta (link nie jest wtedy zużywany). Odebranie ostatniego sklepu kończy jego sesję przy następnym żądaniu (`JwtAuthenticationFilter`). Właściciel loguje się zawsze. W `PUT /api/settings/users/{id}` `storeIds: null` znaczy „bez zmian”.

Kolejne ustawienie = kolejny kafelek i podstrona.

## Import raportu produktów

- Pracownik codziennie wgrywa raport z systemu sklepu (np. `BAZA DO STRONY.xlsx`, arkusz Mercalys, ok. 72 tys. pozycji) na `/import` → `POST /api/stores/{storeId}/imports/products` (multipart `file`, `IMPORTS:EDIT`). Historia: `GET` na tę samą ścieżkę (`IMPORTS:VIEW`). Kartoteka, pary EAN i historia są osobne dla każdego sklepu. Numer sklepu z nagłówka raportu („Numer punktu sprzedaży 10023”) musi się zgadzać z wybranym sklepem, inaczej import jest odrzucany.
- `component/XlsxReader` czyta .xlsx/.xlsm strumieniowo (zip + StAX, bez Apache POI). `component/ProductReportParser` szuka kolumn po nazwie z nagłówka (EAN, NAZWA, ITM8...) i sprawdza „Ilość linii” ze stopki. Jeden błędny wiersz odrzuca cały plik (`rowErrors` w ProblemDetail).
- Kluczem produktu jest **ITM8**, nie EAN. Scalanie idzie w jednej transakcji: `ProductImportService` wczytuje całą kartotekę jako encje i porównuje ją z plikiem w pamięci: nowe kody są dodawane, zmienione pola nadpisywane, a produkty, których zabrakło w pliku, zostają (`last_seen_import_id` wskazuje ostatni import, w którym były). Raport starszy niż ostatnio wgrany jest odrzucany.
- **Pary ITM8 + EAN** (`product_eans`) nigdy nie są nadpisywane ani usuwane: ten sam ITM8 bywa przenoszony na nowy EAN, EAN na nowy ITM8, a system sklepu często poprawia błędnie przypisane EAN-y. Sprzedaż i inne dane z raportów podpinamy pod parę, nie pod sam EAN. `products.ean` to tylko bieżący EAN. Zmiany przypisań z każdego importu trafiają do `product_ean_changes` (`GET /api/imports/products/{id}/ean-changes`).
- **Szkice artykułów z CADBEZP** (V72: `product_drafts`, `product_imports.drafts_matched_count/drafts_removed_count`): po zapisie pliku CADBEZP (wprowadzanie danych i dostawa z bazy) okno `features/data-entry/product-drafts.tsx` pyta „Czy pliki zostały poprawnie utworzone?”. „Tak” = `POST /api/stores/{storeId}/data-entry/product-drafts` z `{fileName, file}` (`DATA_ENTRY:VIEW`, `DataEntryProductFileService.confirm`): każdy artykuł z EAN-em (8-14 cyfr, zapisany bez zer wiodących), którego nie ma w kartotece (bieżący EAN, `product_eans`, multikody), zostaje szkicem z danymi z pliku; oczekujący szkic tego EAN-u dostaje `REPLACED`, toast „Cofnij” = `POST .../product-drafts/undo` z `{ids}` (`CANCELLED`, zastąpione wracają). Import kartoteki (`ProductDraftService.resolve`, w transakcji importu) rozstrzyga tylko szkice utworzone przed datą raportu (Europe/Warsaw): artykuł z tym EAN-em w raporcie = `matched_product_id` (resztę danych ma już `products`), brak = `removed_reason` `MISSING` (znacznik, nie usunięcie). Wynik importu pokazuje obie liczby.
- Kolumna VAT w raporcie to kod stawki z systemu sklepu, a nie procent (`products.vat_code`: 1 = 23%, 2 = 8%, 6 = 5%; 7 przy kaucjach i butelkach). Opcjonalna ostatnia kolumna `CENA_CAD` (V37: `products.cadencier_price`) to cena sprzedaży sztuki narzucona przez centralę (cadencier); bez niej import też przechodzi. CENA_CAD obowiązuje tylko z ostatniego raportu: pusta komórka ją czyści, a artykuł, którego nie ma w pliku, zostaje w kartotece bez niej (`Product.missingFrom`).

## Ceny z kasy (pliki TRACEART)

- System sklepu przy zmianach cen zapisuje w ciągu dnia pliki `TRACEART_RRRRMMDD_HHMMSS_SR…_UT….Traite0` w folderze (pliki z poprzednich dni przenosi do podfolderu `BACKUP`, w którym jest cała historia). Moduł `product`: `component/PriceFileParser`, `PriceFileService`, `PriceFileController`, V64 (`price_file_imports`, w `products`: `sale_price_at`, `promo_price`, `promo_from`, `promo_to`, `price_file_id`). Linia = jeden kod EAN artykułu, 360 znaków stałej szerokości (windows-1250, NUL, CRLF); pola (od zera) rozpoznane na plikach z 02.11.2026 i sprawdzone z kartoteką 10023: 0-12 EAN, 39 kod VAT, 41-49 cena brutto na kasie, 120-125 data początku (DMMRR do prawej, `" 21126"`), 126-131 data końca promocji (`"     0"` = bez promocji), 133-145 ITM8, 306-314 cena regularna w promocji (poza nią `999999.99`). Cena artykułu z linii jego głównego EAN-u z kartoteki, bez niej z kodu o najwyższej cenie (kody z etykiet obniżek 13/15/17… są tańsze; na próbce główny EAN zawsze miał najwyższą).
- **Która cena obowiązuje:** czas z nazwy pliku (lokalny, jak `report_generated_at`). Plik nie starszy niż raport kartoteki, z którego jest cena, ani niż poprzedni plik artykułu ustawia `sale_price` (w promocji regularną), `sale_price_at` i promocję; linia bez promocji ją kończy (`Product.applyPriceFile`). Import kartoteki nadpisuje cenę tylko, gdy raport jest nowszy niż `sale_price_at` (wtedy je czyści; `Product.seenIn`), więc poranny raport wgrany później nie cofa nowszej ceny z kasy. Plik i import kartoteki biorą tę samą blokadę sklepu.
- API `/api/stores/{storeId}/imports/price-files` (`DATA_ENTRY:VIEW` albo `IMPORTS:EDIT`): `GET` (20 ostatnich plików, `activePromotions`), `POST /pending` z `{fileNames}` (których nie wczytano, od najstarszego; pliki sprzed 2026 pomijane, `FIRST_FILE_TIME`), `POST` multipart `files` (plik do 30 MB, przeładowanie wszystkich cen ma 6-7 MB, a front dzieli wysyłkę na paczki do 20 plików i 20 MB; każdy plik raz: nazwa unikalna w sklepie, powtórzony trafia do `skipped`; zły plik = 400).
- Front: `features/data-entry/price-files.ts` (`usePriceFileWatcher` w `AppLayout`: od razu, co 10 min i po powrocie do karty; czyta folder razem z `BACKUP` (rekurencyjnie, `listFolderFiles(key, match, subfolder)` zwraca uchwyty, treść czyta się tylko dla plików, których serwer nie ma), więc po dniach bez aplikacji historia uzupełnia się od najstarszego pliku, z postępem „historia N / M”; zgodę na odczyt po ponownym otwarciu przeglądarki prosi kliknięcie „Zaloguj” (`requestPriceFolderAccess`, wszystkie zapamiętane foldery `price-files:*`) albo pierwsze kliknięcie w aplikacji; stan w module przez `useSyncExternalStore`, wysyłka bez unieważniania wszystkich zapytań), folder do odczytu per sklep (`price-files:<storeId>`, bo w nazwie pliku nie ma sklepu; `lib/saved-folders.ts`: `pickFolder(key, 'read')`, `folderAccess`, `listFolderFiles`), `PriceFileStatus` w nagłówku wprowadzania danych (wybór folderu, „zezwól na odczyt” po ponownym otwarciu przeglądarki, ostatni plik, sprawdź teraz). We wprowadzaniu danych `CatalogProduct.promoPrice`/`promoTo` (trwająca promocja z kasy, a bez niej trwająca promocja z listy promocji, której cena = cena sprzedaży z kartoteki: plik TRACEART starszy niż raport kartoteki jest pomijany, więc promocja rozpoczęta przed raportem ma w kartotece samą cenę promocyjną), w trakcie promocji cena promocyjna jest po prostu aktualną ceną sprzedaży (`DataEntryCatalogRepository.findByEans` oddaje ją jako `salePrice`, więc liczy się z niej marża, idzie do kopiowania i do pliku CADBEZP), a komórka „Cena sprzedaży” jest wtedy pomarańczowa i pogrubiona (`activePromoPrice`). Wiersz pamięta promocję z chwili dodania, więc po wejściu na stronę i po każdym nowym pliku cen (lista z `usePriceFileOverview`) `DataEntryPage` pobiera ceny z kasy znanych artykułów szkicu od nowa (`withCurrentPromo`: promocja i cena sprzedaży, o ile nie zmieniona w tabeli, także powrót do regularnej po końcu promocji; bez kroku cofania).

## Zamówienie garmażu

- Kategoria uprawnień `DELI_ORDERS`, front `/zamowienie-garmazu/*` (zakładki-podstrony: Zamów, Wysłane, Przychodzące, Formularz, `zamowienia/:id`), API `/api/stores/{storeId}/deli-order/...`, gdzie `storeId` to sklep, w którym pracuje użytkownik.
- Formularz należy do sklepu-dostawcy: działy (`order_sections`, zakładki) → kategorie (`order_categories`) → produkty z jego kartoteki (`order_category_products`, z jednostką zamawiania `order_unit` KG/SZT). Układa go `DELI_ORDERS:EDIT` po kliknięciu ołówka; każda zmiana zwraca cały formularz. Zmiany idą po kolei (`scope` mutacji), więc pole wyszukiwarki nie blokuje się w trakcie zapisu: Enter dodaje pierwszy wynik, fokus zostaje, a widok przewija się do nowej pozycji. Do kategorii można wkleić listę z Excela (przycisk „Wklej z Excela” albo wklejenie w wyszukiwarkę): kolumna EAN + jednostka (pusta = kg, `kg`/`szt`), `POST .../categories/{id}/products/paste` szuka po bieżącym EAN-ie z kartoteki i po kodach z multikodów, znanym pozycjom zmienia jednostkę i zwraca nieznalezione EAN-y. Długie działy mają `CategoryNav`: od `lg` spis kategorii w przyklejonej kolumnie obok formularza (`CATEGORY_NAV_GRID`, niczego nie zasłania, sam przewija się do bieżącej kategorii), niżej strzałki po lewej, także w zakładce Zamów. Przejście do kategorii przewija płynnie. Kolejność układa się przeciąganiem za uchwyt (dnd-kit): kategorie w dziale (na czas przeciągania zwijają się do nagłówków), produkty w kategorii i do innej kategorii działu (`PUT .../categories/{id}/position` z `{index}`, `PUT .../categories/{id}/products/{itemId}/position` z `{categoryId, index}`; nowy układ widać od razu, `useMoveInOrderForm`). Przeniesiona pozycja zachowuje id (szkice zamówień trzymają ilości po nim), dlatego kategorię zmienia zapytanie `OrderCategoryProductRepository.moveToCategory`, a nie przepięcie między listami z `orphanRemoval`; produktu, który już jest w kategorii docelowej, nie da się przenieść (409).
- Zaproszenia (`deli_form_invitations`): dostawca zaprasza sklepy, zaproszony sklep przyjmuje (EDIT) i wtedy zamawia z formularza dostawcy. Ze swojego formularza sklep zamawia bez zaproszenia. Cofnięcie zaproszenia odcina formularz, złożone zamówienia zostają.
- Zamówienia (`deli_orders`, `deli_order_items`): składa VIEW, z datą dostawy (≥ dziś, strefa Europe/Warsaw) i ilościami (kg do 3 miejsc, sztuki całe). Dział i kategoria są kopiowane tekstem. Dostawca (EDIT) poprawia ilości (`ordered_quantity` zostaje, `quantity` się zmienia) i potwierdza realizację w oknie `FulfillOrderDialog`: wpisuje zrealizowane ilości (Enter = następne pole, Shift+Enter = poprzednie), a `POST .../orders/{id}/fulfill` z `{items}` zapisuje je razem z realizacją (bez treści: sama realizacja). Potem plik PROTO6 zapisuje się w folderze plików PROTO wybranym raz w przeglądarce (`useProtoFolder`, patrz Pliki PROTO), skąd program sklepu sam go wczytuje. Statusy: NEW (dostawca jeszcze nie otworzył), READ (odczytane: pierwsze otwarcie szczegółów u dostawcy, `POST .../orders/{id}/read`; poprawka i realizacja też je odczytują; własne zamówienie oglądane przez osobę, która je złożyła, zostaje NEW), FULFILLED. Licznik w menu liczy tylko NEW. Dopóki zamówienie nie jest zrealizowane, można je usunąć (`DELETE .../orders/{id}`, zamawiający z VIEW, dostawca z EDIT; zrealizowane tylko właściciel), ale tylko po swojej stronie: `store_deleted_at` / `form_store_deleted_at` ukrywa je z listy tego sklepu, druga strona widzi status „Usunięte”, a usuniętego po którejkolwiek stronie nie da się poprawiać ani realizować. Przywraca `POST .../orders/{id}/restore` (toast „Przywróć”, banner w szczegółach, później logi). Licznik nowych zamówień i zaproszeń: `GET .../overview`, w menu `DeliNewOrdersBadge`.
- **Dopisanie zapomnianego produktu** do niezrealizowanego zamówienia (`POST .../orders/{id}/items` z `{items, extras}` jak przy składaniu; zamawiający z VIEW, dostawca z EDIT, póki zamawiający ma dostęp do formularza, V44): w szczegółach plus „Dopisz” przy każdej kategorii (`AddOrderItemsDialog`) daje produkty tej kategorii formularza, których nie ma w zamówieniu, a w „Spoza formularza” wyszukiwarkę kartoteki dostawcy. Produkt już obecny w kategorii zamówienia daje 409. Pozycja trafia na koniec swojej kategorii z `added_at/by` („dopisane … · kto”).
- **Zmiana daty dostawy** niezrealizowanego zamówienia (`PUT .../orders/{id}/delivery-date` z `{deliveryDate}`, ≥ dziś; zamawiający z VIEW, dostawca z EDIT): `ordered_delivery_date` zostaje datą z chwili złożenia, lista i szczegóły pokazują obie.
- **Łączenie zamówień** (V35): dostawca z EDIT łączy niezrealizowane zamówienia jednego sklepu na ten sam dzień (`POST .../orders/merge` z `{orderIds}`; lista przychodzących i szczegóły podpowiadają takie grupy, `MergeOrders.tsx`). Powstaje nowe zamówienie (`merged_at/by`, status READ, złożone jak najwcześniejsze źródłowe): ten sam produkt w tej samej kategorii i jednostce jest sumowany (`ordered_quantity` i `quantity`), pozycje spoza formularza zostają na końcu działu, dokumenty MM źródłowych są przypięte do połączonego. Źródłowe dostają `merged_into_id`, znikają z list, liczników i z `DocumentResponse.deliOrders` i nie da się ich zmieniać. `POST .../orders/{id}/split` (toast „Cofnij”, przycisk „Rozdziel”) cofa niezrealizowane połączenie: źródłowe wracają, połączone zostaje w bazie z `split_at/by`.
- Wyszukiwarka produktów (`GET .../products?query=`, `repository/ProductSearch`): od 3 znaków bez spacji, każde słowo musi pasować w dowolnej kolejności jako fragment nazwy lub marki, początek EAN (głównego albo każdego obowiązującego z multikodów) albo fragment ITM8; max 20 wyników.
- Kalendarz marki: `components/ui/calendar.tsx`, w formularzach `DateField` (`components/form`). Daty bez godziny jako tekst RRRR-MM-DD (`lib/dates.ts`).
- Pozycje spoza formularza: zamawiający wyszukuje produkty w kartotece dostawcy (`GET .../suppliers/{formStoreId}/products`) i wysyła je w `extras` z jednostką i działem (`sectionId`), bo kartka z wydruku trafia do działu. Dopisuje je na dole zakładki działu; w zamówieniu lądują w tym dziale jako kategoria „Spoza formularza”, za pozycjami z formularza. Ilość 0 nie jest wysyłana. Ceny nie są pokazywane w module.
- Zamówienie jedzie do sklepu na **dokumencie ruchu międzymagazynowego** (typ MM z modułu Dokumenty, w sklepie-dostawcy). Dostawca z EDIT przypina go w szczegółach zamówienia (`POST .../orders/{id}/documents` z `documentId`, podpowiedzi: `GET .../orders/{id}/documents/candidates?query=` - bez zapytania dokumenty z tygodnia przed datą dostawy do dwóch dni po). Można przypiąć kilka. Odpięcie (`DELETE .../orders/{id}/documents/{documentId}`) ustawia `deli_order_documents.unlinked_at/by`, wpis zostaje; „Przywróć” to ponowne przypięcie. Zamawiający widzi przypięte dokumenty (bez kwot), a dokument MM w module Dokumenty pokazuje zamówienia, które na nim jadą (`DocumentResponse.deliOrders`).
- Pliki zamówienia (`GET .../orders/{id}/export/{lst|proto|xlsx|pdf}`, `component/DeliOrderDocuments`): `.lst` z EAN-ami (CRLF), PROTO6 (`PROTO6_RRRRMMDD_HHMMSS_<nr sklepu zamawiającego>_<login>.Traite0`, czas wygenerowania w Europe/Warsaw; w linii EAN i ilość w tysięcznych na 9 cyfrach: 1 szt. = `000001000`, 0,5 kg = `000000500`, CRLF), Excel (EAN, nazwa, marka, ilość, `component/XlsxWriter` bez POI) i PDF (OpenPDF, font DejaVu z `resources/fonts`). W PDF każdy dział zaczyna się na nowej kartce, z pełnym nagłówkiem, własną numeracją Lp., podpisami i stroną liczoną w obrębie działu, bo kartki trafiają do różnych działów. Kategorie mają nagłówki powtarzane na każdej stronie, kolumny Lp. / Towar / Zamówiono / Zrealizowano (puste, na długopis) / Kod. Kod to EAN-13 lub EAN-8, gdy suma kontrolna się zgadza, inaczej Code 128. Wiersze nie dzielą się między strony. Pozycje z ilością 0 są pomijane.

## Dokumenty

- Kategoria `DOCUMENTS`. Front: `/dokumenty` (kafelki typów), `/dokumenty/:typ` (lista, np. `/dokumenty/pl`), `/dokumenty/:typ/:id` (dokument z liniami). API: `GET /api/stores/{storeId}/documents` (typy z liczbą dokumentów + `lastReportGeneratedAt`), `GET .../documents/{typ}?page=&query=&sort=&direction=` (strona po 100, `DocumentPage` z `hasMore`, `matchingCount` i sumami do „Razem”), `GET .../documents/{typ}/{id}`.
- Typy w `entity/DocumentType.java` (nazwa stałej = kod z raportu, trafia do bazy): PZ przyjęcia towaru, PK korekty błędów sklepu, WZ korekty od dostawcy, PL likwidacje, PPP przeniesienia stanów, ZW zwroty do dostawcy, MM ruchy międzymagazynowe (towar jadący do innego sklepu), RWPO potrzeby sklepu, RWREP reprezentacja, RWDA darowizny (pomijane przy imporcie przed 2.11.2026, starsze wymagają ponownego wgrania raportu). **W interfejsie tylko pełne nazwy (`label`, `singular`), nigdy kody.** Ikony kafelków: `features/documents/document-icons.ts`. Typy spoza listy są przy imporcie pomijane (`document_imports.skipped_types`).
- Wszystkie typy mają te same kolumny, więc są w jednej parze tabel: `documents` (unikalne: sklep + typ + numer, z podsumowaniem linii) i `document_lines` (unikalne: dokument + `N° ligne` + ITM8, bo zwroty prasy mają wszystkie linie z numerem 1). Dostawca jest przy linii; w nagłówku tylko wspólny (w likwidacjach, przeniesieniach, reprezentacji linie mają różnych dostawców → „różni dostawcy”).
- Raport wgrywa się w **Imporcie danych** (`/import`): `POST /api/stores/{storeId}/imports/documents` (`IMPORTS:EDIT`), historia `GET` tamże (`IMPORTS:VIEW`). Import danych to siatka kart raportów (patrz „Strona Importu danych”) i wspólna historia na dole.
- Źródło: raport „Statystyka: Wejścia/Wyjścia” z systemu sklepu (.xlsx, np. `Zeszyt2.xlsx`). `component/DocumentReportParser` szuka kolumn po nazwie bez znaków diakrytycznych (`Numéro document interne` → `numero document interne`), bierze numer sklepu z „TRYTOMA Sp. z o.o. - 10023” (musi się zgadzać z wybranym sklepem), okres z „Wybór danych : OD … do …” i sprawdza liczbę linii z „… 6745 linie” (system wlicza do niej wiersz nagłówka). Stopka „Razem:” jest pomijana. Błędna linia zapisywanego typu odrzuca cały plik.
- Raporty obejmują nakładające się okresy: ponowne wgranie aktualizuje nagłówek i linie, nowe linie dopisuje, a brakujących nie usuwa. Numery dokumentów i kody to tekst (zera wiodące, np. `240460000520`). `TVA` to tu stawka w procentach, `0` w „Numéro document fournisseur” oznacza brak.
- **Dokumentów są tysiące:** lista typu przychodzi z serwera stronami po 100 (`useInfiniteQuery`), kolejne strony dociąga `lib/use-load-more.ts`, gdy dojedziesz do końca listy. Wyszukiwanie (`repository/DocumentSearch`: każde słowo jako fragment numeru, dostawcy, jego kodu albo nr dok. dostawcy, bez polskich znaków przez `translate`), sortowanie (klik w nagłówek, `nextSort` z `lib/table-sort.ts`) i sumy „Razem” (`DocumentTotalsRepository`) liczą się w bazie. Potrzeby sklepu, likwidacje, reprezentacja i przeniesienia stanów nie pokazują na liście ani w nagłówku dokumentu dostawcy i nr dok. dostawcy (`showsSupplier` w `features/documents/format.ts`; dostawca zostaje przy liniach). Domyślnie przyjęcia PZ po numerze malejąco (najnowszy bon na górze), a pozostałe typy po dacie malejąco, od najnowszego dokumentu (`defaultSort` w `DocumentsList`); sortowanie po dacie w obrębie dnia idzie po numerze w tym samym kierunku (`DocumentSearch.sort`). Numer to tekst, więc sortowanie po nim idzie najpierw po długości (`Document.numberLength`, `@Formula`), żeby 10000 było większe niż 9999. W przyjęciu PZ numer dokumentu dostawcy da się poprawić (`PUT|DELETE .../documents/pz/{id}/supplier-document-number`, `DOCUMENTS:EDIT`, `features/documents/SupplierDocumentNumber`): `supplier_document_number` to numer obowiązujący, `report_supplier_document_number` ten z raportu, a poprawka (`supplier_document_number_edited_at/by`) przetrwa kolejne importy. Po zmianie front odświeża faktury KSeF, bo po tym numerze faktura staje się „wprowadzona”. Linie jednego dokumentu sortuje i filtruje przeglądarka (`useTableSort`, `matchesSearch`), też rysując je po 100 przy przewijaniu. Ilości bez jednostki (jednostka z raportu opisuje produkt, waga jest w nazwie). Wgrywanie pliku: `components/FileDropZone`, błędy wierszy: `components/ImportError`.

- **Filtry listy** (w bazie, `DocumentSearch`): `product=` szuka artykułu w liniach (każde słowo jako fragment nazwy, marki, EAN-u albo ITM8, wszystkie w tej samej linii), `invoice=with|without` (przyjęcia i korekty od dostawcy: przypięta faktura KSeF albo faktura firmy o numerze = nr dok. dostawcy w PZ), `corrections=with|without` (przyjęcia z przypiętymi korektami), `closed=with|without` (przyjęcia w aktywnym zamkniętym raporcie okresowym razem ze swoim okresem; zmiana przeniesiona do kolejnego raportu się nie liczy), `gratis=with|without|candidate` (przeniesienia stanów zarejestrowane jako gratis, bez gratisu albo nieoznaczone z pozycją GRATIS, czyli „Może być gratisem”), `hideValueFrom=&hideValueTo=&hideValueOf=purchase|sale` (ukrywa dokumenty z kwotą z raportu w przedziale, granice włącznie, jedna wystarczy, odwrócone są zamieniane; wszystkie typy), `hiddenSuppliers=` (powtarzany, kody dostawców ukrytych na liście). Front: drugie pole wyszukiwania pod listą, reszta w oknie „Filtry” w prawym rogu (`features/documents/DocumentFilters`: Raport okresowy Wszystkie / Niezakończone / Zakończone, Faktura, Korekty, Gratis, Ukryj kwoty (Zakup / Sprzedaż brutto, od, do; w przeniesieniach stanów domyślnie sprzedaż, bo zakup jest tam 0), Ukryci dostawcy). Ukryci dostawcy to preferencja przeglądarki per sklep i typ dokumentów (`ui.hiddenDocumentSuppliers` pod kluczem `hiddenSuppliersKey` = `sklep:TYP` + localStorage; stary zapis per sklep trafił do PZ), niezależna od pomijanych w raporcie. Przyjęcie z zamkniętego raportu ma `DocumentSummary.reportClosing` (okres), a na liście kłódkę i szare tło.
- **Przyjęcia za 0 zł** (system sklepu zostawia PZ, na które nic nie przyszło: wszystkie linie z ilością 0) nie są na liście ani w licznikach typów (`DocumentSearch.withoutZeroDeliveries`, `DocumentRepository.countByType`); zostają w bazie i pod adresem dokumentu. Inne typy z 0 zł (np. gratisy) zostają na listach.
- **Stan listy w adresie:** wyszukiwanie (`?szukaj=`, `&produkt=`, wpisywane z opóźnieniem jak zapytanie), filtry (`faktura`, `korekty`, `raport`, `gratis` = `z|bez`, `gratis=moze`; `ukryj_od`, `ukryj_do`, `kwota=zakup|sprzedaz`) i sortowanie (`sortuj=<kolumna>&kierunek=rosnaco|malejaco`, domyślne bez parametrów) są w adresie, więc po wejściu w dokument i powrocie lista jest ta sama, a `ScrollRestoration` wraca w to samo miejsce. Przy nr dok. dostawcy jest `components/CopyButton` (kopiuje do schowka, nie otwiera wiersza).
- **Automatyczne przypisanie faktur** (przycisk nad listą PZ i WZ, `features/documents/AutoInvoiceMatching`, `DOCUMENTS:EDIT` + `KSEF_INVOICES:VIEW`): `GET .../documents/{pz|wz}/auto-ksef-invoices` (`DocumentKsefLinkService.autoMatches`, niczego nie zapisuje, inny typ = 400) bierze dokumenty bez faktury (filtr `invoice=without`; przyjęcia PZ z wartością zakupu > 0, korekty od dostawcy WZ z niezerową) i niewprowadzone faktury KSeF (do PZ faktury, do WZ faktury korygujące; bez pomijanych dostawców) tego samego dostawcy (kod → NIP z listy dostawców), wystawione do 45 dni przed albo po dokumencie (`AUTO_MATCH_DAYS`), z kwotą netto tego samego znaku co wartość zakupu (korekty są zwykle z minusem po obu stronach) i różną najwyżej o 10 zł (`AUTO_MATCH_TOLERANCE`). Pary od najmniejszej różnicy, potem najbliższej daty; przyjęcie i faktura najwyżej w jednej parze. Okno pokazuje bon (przy WZ numer korekty), dostawcę, fakturę i kwoty z zaznaczeniem przy każdej parze; `POST` tamże z `{matches:[{documentId, invoiceId}]}` przypina zaznaczone w jednej transakcji (błąd którejkolwiek, np. 409, wycofuje wszystkie) i zwraca przypięte pary z `attached` (`dto/CorrectionAttachment`: korekty WZ, które trafiły przy tym do przyjęć), toast „Cofnij” = `POST .../auto-ksef-invoices/undo` z tymi parami (odpięcie ze znacznikiem, korekty z `attached` też od przyjęć).
  - **Korekta idzie za fakturą korygowaną, w obie strony** (`DocumentKsefLinkService.attachToCorrectedDelivery`): korekta od dostawcy (WZ) z przypiętą fakturą korygującą trafia do przyjęcia PZ, którego fakturę ta korekta koryguje (`ksef_invoice_corrected` z XML: po numerze KSeF albo NIP-ie sprzedawcy i numerze; faktura przypięta do PZ albo równa jego nr dok. dostawcy), o ile WZ ma dostawcę, nie jest przy żadnym przyjęciu, a takie przyjęcie tego samego dostawcy jest dokładnie jedno. Rusza przy przypięciu faktury korygującej do WZ (z dokumentu, z listy faktur, automatycznie), a `attachPendingCorrections` (WZ z fakturą korygującą, które **nigdy** nie były przy przyjęciu, `DocumentKsefInvoiceRepository.findCorrectionsNeverAttached`; odpiętej ręcznie nie przypina z powrotem) przy przypięciu faktury do PZ, zmianie nr dok. dostawcy, po imporcie dokumentów i w tle (`component/PendingCorrectionsJob`, co `app.ksef.corrections-interval`, gdy `sync-enabled`): tak trafiają do przyjęć korekty przypięte wcześniej i te, których XML odczytano po przypięciu. Przypięte tak korekty mają `linked_by` osoby, która przypięła fakturę (w tle pusty).
- **Raport przyjęć za okres** (`controller/DeliveryReportController`, `service/DeliveryReportService`, front `DeliveryPeriodReport`, najwyżej 366 dni wg daty bonu): Excel z wierszem przyjęcia (data i nr bonu, nr faktury: z KSeF albo nr dok. dostawcy, dostawca, zakup netto, korekty z wartością, zakup po korektach) i pod nim, wcięte o kolumnę i zgrupowane (`XlsxWriter.Row.nested`, grupy otwierają się zwinięte), zakup netto po korektach według rejonów nomenklatury; na końcu „Razem” i rejony za cały okres. `XlsxWriter.Cell` daje pogrubienie i format kwoty.
  - **Podgląd** (`GET .../documents/pz/period-report?from=&to=`, VIEW) niczego nie zapisuje. **Zamknięcie okresu** (`POST .../pz/report-closings` z `{from, to}`, EDIT; okres nie może nachodzić na inny aktywny ani sięgać w przyszłość) zapisuje, co poszło w raporcie (V30: `delivery_report_closings`, `delivery_report_closing_deliveries` z kwotami, rejonami i listą przypiętych korekt), a front od razu pobiera zamknięty raport (`GET .../report-closings/{id}/xlsx`, ze zrzutu, nie z bazy).
  - **Zmiany po zamknięciu:** korekta przypięta albo odpięta później, ponowny import przyjęcia albo jego korekty, przyjęcie dopisane później - zamknięty raport się nie zmienia, a różnica czeka. Podgląd i zamknięcie kolejnego okresu dodają ją na końcu jako „Zmiany w zamkniętych okresach” (kwoty to różnice, opis: z którego okresu, nowe / odpięte korekty), a zamknięcie zapisuje ją we wpisie z `origin_closing_id`, więc przestaje czekać. „Co wiedzą raporty” o przyjęciu = suma wpisów aktywnych zamknięć (korekty z najpóźniejszego). Kandydatów wybiera baza (`DocumentRepository.findChangedDeliveryIds`: `created_at`/`updated_at` przyjęcia, `linked_at`/`unlinked_at` korekty, `updated_at` korekty po zamknięciu), potem porównanie co do grosza. `GET .../report-closings` daje zamknięcia z `pendingChanges`, `GET .../period-report/changes` same zmiany; lista PZ pokazuje baner `PendingReportChanges`.
  - **Pomijani dostawcy** (V31: `delivery_report_excluded_suppliers`, po kodzie dostawcy przyjęcia, nazwa z listy dostawców albo z dokumentów; usunięcie to znacznik): `PUT .../pz/report-excluded-suppliers` z `{supplierCodes}` (EDIT) zastępuje listę i zwraca przegląd zamknięć (`excludedSuppliers`). Na górze okna raportu (`MultiComboboxField`, zapis od razu). Ich przyjęć nie ma w podglądzie, zamknięciu ani wśród dopisanych po zamknięciu; przyjęcie, które już poszło w zamkniętym raporcie, dalej przenosi zmiany. Stopka raportu wymienia pominiętych, a zamknięcie zapisuje ich opis (`delivery_report_closings.excluded_suppliers`).
  - **Korekty w raporcie** są opisane numerem faktury korygującej, nie numerem wewnętrznym (księgowość): przypięte faktury KSeF (z datą wystawienia), potem nr dok. dostawcy korekty, bez obu „brak nr faktury (…numer wewnętrzny…)”.
  - Cofnąć (`DELETE .../report-closings/{id}`, znacznik, toast „Przywróć”) można tylko ostatnie zamknięcie, bo późniejsze mogły przejąć zmiany z wcześniejszych; przywrócić (`POST .../{id}/restore`) tylko, gdy po nim nic nie zamknięto.

- **Ruch międzymagazynowy dla innego sklepu** (V33: `document_transfer_targets`, `service/DocumentTransferService`, `controller/DocumentTransferController`, front `DocumentTransferTarget`, `IncomingTransfers`): w MM osoba z EDIT wskazuje sklep zaprzyjaźniony (`PUT .../documents/mm/{id}/transfer-target` z `{storeId}`; sklep spoza zaakceptowanych znajomych albo inny typ dokumentu daje 400; zmiana sklepu to znacznik na poprzednim wpisie i nowy wpis, `DELETE` cofa, `POST .../transfer-target/restore` przywraca). Okno wyboru podpowiada sklep z przypiętych zamówień garmażu. `DocumentSummary`/`DocumentResponse.transferTarget` (z `enteredAt`), na liście MM plakietka „Dla …”. Sklep docelowy (bez dostępu do sklepu wysyłającego) widzi je pod `/api/stores/{storeId}/incoming-transfers` (VIEW: `pending` wszystkie, `entered` ostatnie 30, `/count` do licznika w menu przy Dokumentach, `/{id}` z liniami) i oznacza `PUT .../incoming-transfers/{id}/entered` z `{entered}` (EDIT, cofnięcie = `false`). **Przyjęte ilości** (V43: `document_transfer_received_lines`, `document_transfer_targets.received_at/by`): `POST .../incoming-transfers/{id}/receive` z `{items:[{lineId, quantity}]}` (EDIT, ilość ≥ 0, do 3 miejsc; linia pominięta = ilość z dokumentu bez minusa, poprawka nadpisuje) zapisuje, ile naprawdę przyjechało, i oznacza dokument jako wprowadzony. Pliki w przyjętych ilościach: `GET .../incoming-transfers/{id}/export/{proto|xlsx}` (VIEW): PROTO6 (`common/component/ProtoFile`, wspólny z garmażem; pochodzenie w nazwie = sklep wysyłający, linie bez EAN-u pominięte) i Excel (w dokumencie, przyjęto, różnica). Front: okno `ReceiveTransferDialog` („Wpisz przyjęte ilości”, Enter = następne pole) po zatwierdzeniu zapisuje PROTO6 w folderze plików PROTO (ten sam co garmaż), w szczegółach „Pobierz” i kolumna „Przyjęto” z różnicą. Front: baner nad kafelkami Dokumentów, `/dokumenty/do-wprowadzenia` i `/dokumenty/do-wprowadzenia/:id` (ceny i wartości zakupu bez minusa, bo w sklepie wysyłającym MM to wydanie).

### Korekty przyjęć i wydruk bonu dostawy

- **Korekta** błędu sklepu (PK) albo od dostawcy (WZ) przypina się do przyjęcia PZ, którego dotyczy (`delivery_corrections`, V28, `service/DeliveryCorrectionService`, `DocumentType.isDeliveryCorrection()`), bo raport nie mówi, którą dostawę poprawia. Z obu stron: `GET .../documents/{typ}/{id}/corrections/candidates?query=`, `POST .../corrections` z `documentId` (druga strona), `DELETE .../corrections/{documentId}` (`DOCUMENTS:EDIT`); odpięcie to znacznik, „Przywróć” to ponowne przypięcie. Korekta poprawia jedno przyjęcie (inne daje 409), przyjęcie może mieć kilka korekt, a dostawca musi się zgadzać (400). Podpowiedzi zawsze od tego samego dostawcy (przy dokumencie bez wspólnego dostawcy: dostawca większości linii): do przyjęcia wolne korekty do roku po nim, do korekty przyjęcia ze 120 dni przed nią, najpierw z największą liczbą wspólnych ITM8 (`commonItems`).
- **Przyjęcie po korektach** (`DeliveryCorrectionService.corrected`, liczone w locie, więc ponowny import korekty od razu je zmienia): ilości i kwoty w korektach są ze znakiem (PK zamienia artykuły, WZ to zwykle obniżka ceny z ilością 0), więc do linii przyjęcia dochodzą linie korekt z tym samym ITM8, artykuły spoza przyjęcia są dopisane na końcu, cena zakupu = wartość / ilość, marża % od sprzedaży brutto. `DocumentResponse.corrected` (linie z `originalQuantity` / `originalPurchaseValue`), `correctionTotals` (też na liście), w korekcie `correctionOf`. Szczegóły PZ pokazują domyślnie linie po korektach (przełącznik „Po korektach”), lista PZ wartości po korektach z przekreśloną z raportu. Raporty i „Razem” liczą się dalej z raportu.
- Przy przyjęciu są też **faktury KSeF jego korekt od dostawcy** (`DocumentKsefLinkService.invoicesWithCorrections`, `LinkedKsefInvoice.viaCorrection`): nie liczą się do jednej faktury przyjęcia i odpina się je w korekcie.
- **Korekty z KSeF przy bonie** (`service/DeliveryKsefCorrectionService`, `controller/DeliveryKsefCorrectionController`, front `DeliveryKsefCorrections` w sekcji faktur PZ): korekta z KSeF należy do przyjęcia, gdy koryguje jego fakturę (przypiętą albo po numerze): po numerze KSeF faktury korygowanej, a bez niego po NIP-ie sprzedawcy i numerze (bez względu na wielkość liter). `GET .../documents/pz/{id}/ksef-corrections` (VIEW + `KSEF_INVOICES:VIEW`) daje korekty z WZ, które mają tę fakturę, podpowiedzi WZ (ten sam dostawca, do 45 dni od faktury, kwota netto w granicach 10%, min. 1 zł; bez WZ z fakturą KSeF i przypiętych do innego przyjęcia) i `pendingCount` (korekty dostawcy bez odczytanego XML). WZ w raportach nie mają numeru dokumentu dostawcy, więc po numerze się nie łączą. `POST .../ksef-corrections/{invoiceId}/document` z `{documentId}` (EDIT + `KSEF_INVOICES:VIEW`) przypina fakturę do WZ i WZ do przyjęcia (`attached` = WZ przypięta teraz), toast „Cofnij” = `DELETE .../document/{documentId}?detach=`. Korekty z KSeF bez WZ nie zmieniają zgodności kwot (tylko informacja); ujęte widać wśród faktur („z korekty …”).
- **Zgodność kwot z fakturą** (`service/InvoiceAmountCheckService`, `InvoiceAmountCheck` w `DocumentSummary` i `DocumentResponse` przyjęć z fakturą): suma netto faktur przyjęcia (przypiętych, dopasowanych po numerze i faktur jego korekt od dostawcy) vs wartość zakupu netto po korektach; różnica do 1 zł w górę lub w dół to zgodność (`InvoiceAmountCheckService.TOLERANCE`). Niezgodność widać na liście PZ i w szczegółach; osoba z EDIT ją potwierdza (`PUT|DELETE .../documents/pz/{id}/amount-confirmation`, `document_amount_confirmations`, V29, cofnięcie to znacznik). Potwierdzenie zapisuje obie kwoty i obowiązuje tylko dla nich: zmiana faktur, korekt albo importu przywraca ostrzeżenie.
- **Porównanie z XML faktury** (`GET .../documents/pz/{id}/invoice-comparison`, VIEW + `KSEF_INVOICES:VIEW`, `service/InvoiceComparisonService`, front `InvoiceComparisonPanel`): przy niezgodnej i niepotwierdzonej kwocie rusza samo po wejściu do PZ, przy zgodnej na przycisk. XML faktur (własnej i faktur korekt od dostawcy) z `ksef_invoice_xml`, za pierwszym razem z KSeF (`KsefInvoiceService.xml`, każda faktura we własnej transakcji; niedostępna, np. limit, trafia do `unavailable`). Pozycje faktur (`KsefInvoiceReader.Line.gtin`; wiersze „przed korektą” odejmowane) łączą się z artykułami przyjęcia po korektach po ITM8: EAN z linii przyjęcia i wszystkie EAN-y artykułu z `product_eans`, EAN bez zer wiodących (GTIN-14 = EAN-13). Wiersz: przyjęcie i faktura (ilość × cena, wartość netto), różnica, status (zgodne do grosza, inna cena, inna ilość, brak na fakturze, brak w przyjęciu, pozycja bez EAN); najpierw różnice od największej.
- **Ręczne łączenie w porównaniu** (V32: `invoice_comparison_matches`, `POST .../documents/pz/{id}/invoice-comparison/matches` z `{invoiceKeys, itm8s}`, `DELETE .../matches/{matchId}` (znacznik), `POST .../{matchId}/restore`, `DOCUMENTS:EDIT`): czego EAN nie połączy (zły kod od dostawcy, pozycja przyjęcia rozbita na fakturze na kilka, pozycja bez kodu), łączy się zaznaczeniem wierszy i „Połącz zaznaczone”. Klucz pozycji faktury: `ean:<EAN bez zer wiodących>` albo `name:<nazwa>`. Grupy liczy union-find (`InvoiceComparisonService.Groups`); pozycja faktury z ręcznego połączenia nie łączy się już sama po EAN-ie. Wiersz ma `itm8s`, `invoiceKeys`, `matchIds`.
- **Faktura spoza KSeF** (V32: `document_manual_invoices`, `service/DocumentManualInvoiceService`, `controller/ManualInvoiceController`, `DocumentType.canHaveManualInvoice()`: PZ, PK, WZ): dostawca z listy dostawców (albo dodany ręcznie) i numer, opcjonalnie data. `POST .../documents/{typ}/{id}/manual-invoices`, `DELETE .../{invoiceId}` (znacznik), `POST .../{invoiceId}/restore` (`DOCUMENTS:EDIT`, bez `KSEF_INVOICES`). Przyjęcie ma jedną fakturę: z KSeF albo spoza (druga daje 409 z obu stron). W oknie „Przypnij fakturę” pod listą z KSeF jest „Faktury nie ma w KSeF? Wpisz ją ręcznie”; bez KSeF (PK, brak uprawnienia) okno od razu pokazuje formularz. `manualInvoices` w `DocumentSummary`/`DocumentResponse`, filtr `invoice=with` ją liczy, raport przyjęć bierze jej numer, gdy nie ma faktury z KSeF. Wybór dostawcy: `features/documents/SupplierPicker` (też w gratisie). **Plik faktury** (V39: `document_manual_invoice_files`, treść `bytea` w PostgreSQL, bo plików jest mało i idą do kopii razem z bazą): PDF albo zdjęcie JPG/PNG do 10 MB (`DocumentManualInvoiceService.MAX_FILE_BYTES`), typ rozpoznawany po pierwszych bajtach, nie po nazwie. `PUT .../manual-invoices/{invoiceId}/file` (multipart `file`, EDIT; wymiana = znacznik na poprzednim, najwyżej jeden aktywny), `GET` tamże (VIEW, `inline` + `nosniff`), `DELETE` (znacznik), `POST .../file/restore`. `ManualInvoice.file` niesie tylko opis (nazwa, typ, rozmiar; listy czytają projekcję bez treści). Front: plik wybiera się w formularzu faktury (dołączany zaraz po zapisie) albo przy fakturze w dokumencie (pobierz, drukuj PDF, wymień, usuń z „Przywróć”); plakietka faktury na liście pobiera plik.
- **Wydruk bonu dostawy** (`GET .../documents/pz/{id}/delivery-note`, VIEW, `component/DeliveryNotePdf`, A4 poziomo, układ bonu z systemu sklepu): dostawca z listy dostawców, „BON DOSTAWY NR” = `Document.bonNumber()`, linie (ITM8, EAN, nazwa, VAT, ilość, ceny zakupu i sprzedaży, wartość netto, marża %), sumy z marżą, wycena w cenach zakupu (VAT liczony od sumy netto w stawce) i sprzedaży według stawek, wycena według rejonów nomenklatury, lista uwzględnionych korekt, podpisy. Wszystko po korektach; zmienione linie mają gwiazdkę i wartości sprzed korekty.

### Dostawcy i gratisy

- **Lista dostawców** (`suppliers`, per sklep) pochodzi z raportu „Lista dostawców” z systemu sklepu (np. `nananna.xlsx`, arkusz Mercalys: „… - Numer punktu sprzedaży 10023”, „Data : 25/10/2026 12:46:21”, kolumny Kod dost. … Ilość ITM, stopka „Ilość linii: 317”). Wgrywa się ją w Imporcie danych (trzecia karta): `POST /api/stores/{storeId}/imports/suppliers` (`IMPORTS:EDIT`), `GET` tamże zwraca liczbę dostawców i historię. `component/SupplierReportParser`, scalanie w `SupplierService` po **Kod dost.** (ten sam co `supplier_code` w liniach dokumentów): nowi dodawani, znani nadpisywani, brakujący zostają (`last_import_id`), starszy raport odrzucany. Listy nie trzeba wgrywać codziennie, więc jej karta w Imporcie danych nie ma znacznika aktualności (tylko „lista z …”).
- Dostawcę spoza systemu sklepu dodaje się ręcznie (`POST /api/stores/{storeId}/suppliers`, `SUPPLIERS:EDIT` albo `DOCUMENTS:EDIT`): bez kodu, jest tylko w aplikacji, nazwa unikalna w sklepie. Lista do wyboru: `GET .../suppliers` (`SUPPLIERS:VIEW` albo `DOCUMENTS:VIEW`, wszyscy naraz, filtruje przeglądarka).
- **Moduł Dostawcy** (kategoria `SUPPLIERS`, front `/dostawcy` i `/dostawcy/:id`, `features/suppliers`, `SupplierDirectoryService`, V59): lista dostawców sklepu (z listy i dodani ręcznie, wyszukiwarka i filtr w adresie: `?szukaj=&rodzaj=lista|reczni`) i karta dostawcy. Dane z raportu (kod, nazwa, NIP, adres) są per sklep i tylko do odczytu (u dodanego ręcznie edytowalne). **Strona, telefon, e-mail, notatki i kontakty są wspólne dla firmy** (`supplier_profiles`, `company_key` = NIP sklepu, sklep bez NIP-u sam dla siebie): dostawcę w sklepach firmy wskazuje `supplier_key` (`code:<kod>`, u dodanego ręcznie `nip:<NIP>` albo `name:<nazwa>`), profil powstaje przy pierwszej zmianie i zostaje przypięty (`suppliers.profile_id`), więc zmiana nazwy go nie odcina; karta pokazuje `sharedWithStores`. Kontakty (`supplier_contacts` przy profilu, `SupplierContactKind`: przedstawiciel, zamówienia / biuro, księgowość, reklamacje, inny; wystarczy imię i nazwisko, telefon albo e-mail): `GET .../suppliers/{id}` (VIEW), `PUT .../suppliers/{id}` (strona dostaje `https://`), `POST .../{id}/contacts`, `PUT|DELETE .../contacts/{contactId}` (znacznik), `POST .../contacts/{contactId}/restore` (EDIT); każda zmiana zwraca całą kartę. Lista ma `representative` (pierwszy przedstawiciel) i `contactCount`. Import listy profili nie rusza.
- **Gratis:** przeniesienie stanów (`DocumentType.canBeGratis()`, tylko PPP) można zarejestrować jako gratis od dostawcy: `PUT .../documents/{typ}/{id}/gratis` z `{supplierId, kind, reportMonth}` (`DOCUMENTS:EDIT`; zmiana dostawcy, rodzaju albo miesiąca daje poprzedniemu wpisowi znacznik i nowy wpis), `DELETE` cofa (znacznik), `POST .../gratis/restore` przywraca ostatni. `kind` (V40, `GratisKind`): `TRADE` za handel / ekspozycję albo `LOSSES` pokrycie strat. `reportMonth` (RRRR-MM, `document_gratis.report_month` = pierwszy dzień) to miesiąc, którego gratis dotyczy, wybrany ręcznie; pusty albo równy miesiącowi daty dokumentu = miesiąc daty dokumentu (`DocumentGratis.getEffectiveMonth`, w odpowiedzi `effectiveMonth`). Wartością gratisu jest sprzedaż brutto dokumentu (`documents.sale_value_gross`), nie kopia, więc późniejsze importy ją poprawiają. Dokument z linią o nazwie zawierającej „GRATIS” ma `has_gratis_line` (liczone w `Document.recalculateSummary`), a lista pokazuje „Może być gratisem”. W oknie wyboru podpowiadany jest dostawca większości linii (bez pozycji GRATIS, którą wystawia sam sklep), a obok 5 ostatnich dostawców artykułów z dokumentu z przyjęć PZ (`GET .../gratis/supplier-suggestions`, `DocumentLineRepository.findRecentSuppliers`, od najświeższej dostawy; baza (538, 88110) rozbita na marki artykułów, bo gratis daje producent; klik wybiera dostawcę z listy sklepu).

## Nomenklatura i sprzedaż (V24)

- **Nomenklatura** (`nomenclatures`, per sklep, z PDF-u „LISTA NOMENKLATUR”, np. `nomenklatury.pdf`, stopka „2358 linie”): trzy poziomy, kod rośnie o dwie cyfry: rejon `01` → rodzina `0101` → podrodzina `010101` (`NomenclatureLevel`, `parent_id`, kolumny liczone `region_code`/`family_code`). Wgrywa się w Imporcie danych (piąta karta, PDF): `POST /api/stores/{storeId}/imports/nomenclatures` (`IMPORTS:EDIT`), `GET` tamże: liczba rejonów, rodzin, podrodzin i historia. `component/NomenclatureReportParser` czyta PDF przez OpenPDF: zwykły odczyt tekstu skleja komórki, więc `common/component/PdfCells` (własny `TextAssembler`, wspólny z listą promocji; PDF czyta z bajtów, bo plik zmapowany przez OpenPDF blokuje na Windowsie usunięcie pliku tymczasowego) zbiera napisy (każda komórka to osobny napis) z pozycją, wiersz = napisy na jednej wysokości, komórka trafia do kolumny o najbliższym nagłówku. Strony są obrócone; oś wiersza rozpoznaje po nagłówkach. Tekst dekoduje przez `ParsedText.getAsPartialWords()` (samo `getText()` wywraca się na fontach Identity-H). Sprawdza numer sklepu („TRYTOMA Sp. z o.o. : 10023”), datę („lun. 26/10/2026 - 14:43:41”), liczbę linii, powtórzone kody i rodzica każdej pozycji. `NomenclatureService` scala po kodzie (rodzic przed dziećmi), brakujących nie usuwa (`last_import_id`), starszy raport odrzuca.
- Produkt należy do podrodziny: `products.nomenclature` „01 01 01” daje kolumny liczone przez bazę `region_code`, `family_code`, `subfamily_code` (w `Product` tylko do odczytu). Raport łączy produkt z nomenklaturą po `(store_id, kod)` albo przez widok `product_nomenclature` (produkt + id i nazwy rejonu, rodziny, podrodziny).
- **Sprzedaż** (`sales`): raport „Zestawienie: Wejścia/Wyjścia” wg artykułu i dnia, sprzedaż po rabacie, FIFO (np. `sprzedaz.xlsx`: „PDV: 10023 …  Data: … Godzina: …”, „Wybór Danych: Od … do …”, kolumny ITM8 Prio, EAN Prio, Nazwa, Marka, Data, Ilość, Wartosc FIFO, Wartość ceny sprzedaży, Wartość VAT, Wart.Marza FIFO, % Marża). Wgrywa się w Imporcie danych (czwarta karta): `POST /api/stores/{storeId}/imports/sales` (`IMPORTS:EDIT`), `GET` tamże: liczba wierszy, zakres dni, historia.
  - **Zapisujemy tylko zakończone dni.** Raport wygenerowany 27.10 ma niepełną sprzedaż z 27.10 (sklep jeszcze sprzedawał), więc wiersze z dnia wygenerowania raportu (i późniejszych; bez daty w nagłówku - z dzisiaj, Europe/Warsaw) nie trafiają do `sales`, tylko do licznika `sales_imports.incomplete_count` (`SalesImportService.firstIncompleteDay`, `SalesReportBatch.before`). Ten dzień dopisze raport z 28.10. Niepełne dni zapisane przed tą zasadą V27 przeniosła do `sales_incomplete` (nie usunęła) i odjęła od `created_count`. Raporty sprzedaży sięgają najwyżej do wczoraj.
  - **Raz zapisana sprzedaż jest jedynym źródłem prawdy:** nie zmienia się jej ani nie nadpisuje. Import tylko dopisuje dni artykułów, których jeszcze nie ma; już zapisane pomija, nawet gdy plik ma inne wartości (`sales_imports.existing_count`, z tego `conflict_count` niezgodnych z zapisanymi, pokazywane w wyniku importu). Wyzwalacz `sales_read_only` blokuje w bazie każdy UPDATE, DELETE i TRUNCATE na `sales`, a encja `Sale` jest `@Immutable`. Kolejność i wiek raportów nie mają znaczenia (starszy plik może tylko dopisać brakujące dni). Odrzucany jest raport innego sklepu, data spoza okresu z nagłówka, powtórzony ITM8 + EAN + dzień w pliku i plik bez ostatniego wiersza „Ilość linii:N” (tekst w kolumnie ITM8, rozpoznawany po całej komórce, bo nazwy produktów mają np. „96 LINIA”; wiersz sumy nad nim ma pusty ITM8) albo z liczbą niezgodną z plikiem.
  - Wiersz = sklep + dzień + ITM8 + EAN (V25: ten sam ITM8 sprzedaje się w jednym dniu pod kilkoma EAN-ami; unikalność `sales_key` z `nulls not distinct`, bo EAN bywa pusty; bez uuid i znaczników czasu, bo wierszy są miliony), `import_id` to import, który go zapisał, `ean` to EAN Prio (para z `product_eans`). Bez FK do produktu: sprzedaż artykułu spoza kartoteki też jest zapisywana, raport łączy ją z `products` po `(store_id, itm8)`. Kwoty: `cost_value` (FIFO netto), `sale_value_gross` (brutto po rabacie), `vat_value`, liczone `sale_value_net`, `margin_value`, `margin_percent` jak w raporcie. **Raporty liczą całą sprzedaż ITM8 z dnia** (suma po EAN-ach): widok `sales_by_article` (V26; sklep, dzień, ITM8, sumy ilości i kwot; % marży liczy raport z sum). Raporty za okres korzystają z klucza `(store_id, sale_date, itm8, ean)`, historia artykułu z indeksu `(store_id, itm8, sale_date)`.
  - **Import jest pod duże pliki** (start: ok. 2 mln wierszy w 4 plikach, potem 15-20 tys. dziennie): `component/SalesReportParser` czyta strumieniowo i oddaje paczki po 5000 wierszy ułożone kolumnami (`SalesReportBatch`), a `SaleRepository.insertNew` zapisuje paczkę jednym zapytaniem (`unnest` tablic + `on conflict do nothing`, w tym samym zapytaniu porównanie z wierszami zapisanymi wcześniej). Bez encji na wiersz. Całość w jednej transakcji: błędny wiersz gdziekolwiek wycofuje cały plik. Pomiar: 500 tys. nowych wierszy ok. 19 s, ponowne wgranie tego samego pliku ok. 11 s.

## Raporty sprzedaży

- Kategoria `SALES` („Sprzedaż i raporty”), front `/sprzedaz`: siatka kafelków raportów (`features/sales/ReportsGrid.tsx`, lista `REPORTS`; kolejny raport = kolejny kafelek i podstrona w `SalesPage`). API `/api/stores/{storeId}/reports` (`SALES:VIEW`): `GET` zakres dni sprzedaży i data najnowszego raportu, `service/SalesReportService`.
- **Porównanie sprzedaży** (`/sprzedaz/porownanie`, `GET .../reports/sales-comparison?previousFrom&previousTo&currentFrom&currentTo&parent=&unassigned=`): okres porównywany w całości (2 dni do 2 dni, nie dzień po dniu), **domyślnie z tym samym okresem rok wcześniej, w te same dni tygodnia**: 364 dni (52 tygodnie) wstecz, np. pon.-niedz. 19-25.10.2026 z pon.-niedz. 20-26.10.2025 (`YEAR_AGO_DAYS` w `features/sales/periods.ts`). „Porównaj z” (`?porownaj=rok|poprzedni|tydzien|wlasny&por_od=&por_do=`, `CompareMode`, `comparePeriods`) daje też poprzedni okres (dzień przed, tydzień przed, poprzedni miesiąc: pełny z pełnym, w toku te same dni od 1., własny okres: tyle samo dni tuż przed), tydzień temu (tylko dzień i własny okres) albo własny okres porównania (startuje od tego, z czym porównywano); różna liczba dni daje ostrzeżenie. Nagłówki („Rok temu”, „Poprzedni”…) idą z `COMPARE_LABELS`. Kolumny: rok temu / aktualny / zmiana %. Okres wybiera front (w adresie `?okres=dzien|tydzien|miesiac|wlasny&data=` albo `&od=&do=`): dzień, tydzień, miesiąc (w toku ucięty do ostatniego dnia ze sprzedażą) albo własny okres, najwyżej 366 dni. Tydzień to zawsze pełny, zakończony tydzień pon.-niedz.: domyślnie ostatni, a dzień z tygodnia w toku przesuwa się na ostatni pełny (`resolveAnchor`, `lastCompleteWeekEnd`). Strzałka „następny” nie wchodzi w tydzień w toku. Backend przyjmuje dowolne dwa okresy.
- Drzewo wg nomenklatury: bez `parent` rejony, z kodem rejonu rodziny, rodziny podrodziny, podrodziny artykuły (najpierw najlepiej sprzedające się teraz). Kod grupy to początek `products.subfamily_code`, nazwa z `nomenclatures` (bez wgranej nomenklatury widać same kody). Sprzedaż artykułów spoza kartoteki to wiersz „Bez nomenklatury” na końcu (`unassigned=true` daje jego artykuły). Każdy poziom to osobne zapytanie przy rozwinięciu: rejony całego sklepu i „Bez nomenklatury” sumują sprzedaż całego sklepu (`SaleRepository.ARTICLE_SALES`: suma ITM8 po EAN-ach w obu okresach), a rozwinięta grupa czyta tylko swoje artykuły od kartoteki po indeksach (sklep, ITM8, miesiąc / dzień) (`GROUP_ARTICLE_SALES`). Przed sumami miesięcznymi na produkcji rok do roku: cały sklep ok. 0,7 s, rejon ok. 0,45 s, rodzina ok. 60 ms, podrodzina ok. 20 ms.
- **Sumy miesięczne** (V54: `sales_monthly`, sklep + pierwszy dzień miesiąca + ITM8, sumy ilości i kwot): pełne miesiące okresu raporty biorą stąd, a dni niepełnych miesięcy na brzegach ze sprzedaży dziennej (`PERIOD_BOUNDS`, `STORE_PARTS` / `GROUP_PARTS` w porównaniu, ten sam podział w `sumByRegion` podsumowania; gratisy mają pełne miesiące i czytają tylko `sales_monthly`). Rok do roku to ok. 0,5 mln wierszy miesięcznych zamiast ok. 2,6 mln dziennych. Tabelę utrzymuje wyzwalacz `sales_monthly_add` (po każdym INSERT do `sales`, na poziomie polecenia z tabelą przejściową: dodaje wstawione kwoty do sum miesiąca), więc import się nie zmienił; sprzedaż jest tylko dopisywana (`sales_read_only`), więc sumy zawsze zgadzają się z `sales`. Wykresy dzień po dniu czytają dalej `sales`. Transakcje raportów (porównanie, wykres, podsumowanie, gratisy) zaczynają od `SaleRepository.tuneForReport()`: bez JIT (ok. 100 ms kompilacji przy roku) i `work_mem` 32 MB (przy domyślnych 4 MB sumy artykułów lądują na dysku). Front trzyma wyniki raportów 10 min (`REPORT_STALE_TIME`), bo import i tak unieważnia wszystkie zapytania.

## Kalkulator cen garmażu

- Kategoria `DELI_PRICES`, front `/kalkulator-garmazu` (lista z wyszukiwarką, na górze „Odśwież ceny” i „Eksport do Excela”), `/kalkulator-garmazu/nowa` i `/kalkulator-garmazu/:id` (kreator), API `/api/stores/{storeId}/price-calculations` (`GET` lista, `/{id}`, `/finished-products`, `/products?query=`, `/export/xlsx`: VIEW; `POST`, `PUT /{id}`, `DELETE /{id}`, `POST /{id}/restore`, `POST /refresh-prices/preview?calculationId=`, `POST /refresh-prices`: EDIT). Usunięcie to znacznik (`deleted_at`), toast „Przywróć”.
- Kalkulacja (`price_calculations`, `price_calculation_items`) jest dla **gotowego wyrobu z kartoteki** (`product_id`, tylko nomenklatury 24, 36, 46: `PriceCalculationService.FINISHED_NOMENCLATURES`, NOM „36 60 02” → dział 36), jeden wyrób = jedna aktywna kalkulacja. Nazwa to kopia nazwy wyrobu. Tryb `PER_KG` (ilości na 1 kg wyrobu) albo `PER_BATCH` (na cały przepis, z `batch_yield` kg wyrobu), składniki z kartoteki z ilością. `PUT` zastępuje listę składników; każdy produkt najwyżej raz.
- **Cena składnika** (`component/IngredientPricing`): z ostatniej dostawy, czyli najnowszej linii przyjęcia PZ z tym ITM8 w sklepie (`DocumentLineRepository.findPricedLines`), a gdy produktu nie było w dostawach, z kartoteki. Cena zakupu w PZ i w kartotece dotyczy sprzedawanej sztuki, a WAGA (`net_content`) mówi, ile w niej jednostki, więc koszt jednostki to cena / `net_content` (`Product.unitCostOf`, np. bita śmietana 55 g za 1,69 zł → 30,73 zł/kg). Ilość wpisuje się w `Product.getCostUnit()`: kg, L, szt.; artykuły wagowe „A.Wa” liczą się na kg.
- **Waga sztuki:** warzywa na sztuki (JED szt., WAGA 1 = 1 sztuka, cena za sztukę) wpisuje się w sztukach. Przy takim składniku kreator ma pole „1 szt. waży ok. … kg” (`products.piece_weight`, z autorem i datą, zapamiętane dla produktu w sklepie, import raportu go nie rusza; przychodzi w `items[].pieceWeight`, `null` czyści). Waga nie zmienia kosztu, tylko wlicza sztuki do **wagi surowców** przepisu. To waga przed obróbką, a nie gotowego wyrobu (z 3 kg surowców wychodzi np. 1 kg), dlatego nie podpowiada wydajności. Przy całym przepisie kreator pokazuje „Wydajność” = wydajność / waga surowców, gdy znane są wagi wszystkich składników.
- **Ceny są zapamiętywane** w składniku (`unit_cost`, `price_source` DELIVERY/CATALOG, `price_document_id`, `priced_at`): nowy składnik dostaje aktualną cenę, przy zapisie znane składniki zachowują swoją. Zmienia je dopiero „Odśwież ceny” (`prices_refreshed_at`).
- **Własna cena** (`manual_price`, z autorem i datą) zastępuje wyliczoną w eksporcie; `salePrice` w odpowiedziach to cena do eksportu, `calculatedPrice` wyliczona. **„Odśwież ceny” ma dwa kroki** (`RefreshPricesButton`): podgląd bez zmian w bazie, potem zatwierdzenie z decyzjami. Pyta (`PriceCalculationService.needsDecision`) o kalkulacje z własną ceną, gdy wyliczona wychodzi inna niż dotąd, i o te z ceną wyliczoną, gdy zmienia się o ≥ 10% (`PRICE_CHANGE_THRESHOLD_PERCENT`); reszta odświeża się bez pytania. `KEEP` zostawia cenę sprzed odświeżenia (wyliczona zostaje zapisana jako własna), `ACCEPT` bierze nową wyliczoną i kasuje własną. Gdy od podglądu doszła kalkulacja wymagająca decyzji, zatwierdzenie zwraca 409.
- **Cena sprzedaży 1 kg** (`PriceCalculation.getSalePrice()`, ten sam wzór w `format.ts` → `salePrice`): koszt 1 kg (przy `PER_KG` suma składników, przy `PER_BATCH` suma / wydajność) × (100 + `MARKUP_PERCENT` = 60)% × (100 + VAT)%, zaokrąglone **w górę** do ,99 zł (15,40 → 15,99; 16,00 → 16,99). VAT na kalkulację: 0, 5, 8 albo 23%, domyślnie 5%. Eksport `.xlsx`: EAN, Nazwa, Cena sprzedaży, VAT %.
- Kreator (`features/deli-prices/CalculationEditor.tsx`) przelicza na bieżąco; wyrób wybiera `FinishedProductPicker` (wszystkie wyroby naraz, filtr po nazwie, marce, EAN), składniki panel po prawej. Niezapisane zmiany pilnuje `useBlocker` i `beforeunload`; „Odśwież ceny” w kreatorze jest wyłączone, dopóki są niezapisane zmiany.

- Kategoria `KSEF_INVOICES`, front `/faktury-ksef` (lista) i `/faktury-ksef/ustawienia` (tylko EDIT), API `/api/stores/{storeId}/ksef/...`: `GET` (nagłówek: czy połączony, ostatnie pobranie, IDWew sklepu), `GET /invoices` (VIEW, strony po 100), `PUT|DELETE /invoices/{id}/entered`, `POST /sync` (202, zleca pobieranie w tle i zwraca nagłówek), `/settings/**` (EDIT), `GET /invoices/{id}/xml` (VIEW, oryginał prosto z KSeF), `GET /invoices/{id}/pdf` (VIEW, PDF do czytania i wydruku).

Tytuł sekcji jest wierszem nagłówka jej tabeli, więc nie zostaje sam na dole strony. Plik, którego nie da się odczytać, daje 400. „Drukuj fakturę” w menu faktury ładuje ten PDF do ukrytej ramki i od razu otwiera okno drukowania (`printFile` w `lib/api.ts`), bez zapisu na dysk.
- **Faktury są wspólne dla firmy (NIP), nie dla sklepu** (V20): `ksef_invoices.nip` (unikalne: NIP + numer KSeF), kursor i wynik pobierania w `ksef_sync_states` (per NIP), token KSeF w `KsefSessionService` też per NIP. Pobieranie idzie raz na NIP, a każdy sklep z połączeniem tej firmy od razu widzi jej faktury (według swoich IDWew). Przy sklepie zostaje to, co jego: połączenie (certyfikat), IDWew, pomijani dostawcy, PZ-ki i ręczne „wprowadzona” (`ksef_invoice_entries`, cofnięcie usuwa wpis).
- **Połączenie per sklep** (`ksef_connections`, kontekstem jest NIP firmy): osoba z EDIT wgrywa certyfikat KSeF do uwierzytelniania (.crt) i klucz (.key, PKCS#8 zaszyfrowany hasłem: PBES2/AES-256, odczytuje go sama Java w `component/KsefCredentials`), wpisuje hasło i NIP firmy (kontekst logowania, z sumą kontrolną). Klucz zostaje w bazie tak, jak przyszedł, hasło jest szyfrowane AES-GCM kluczem `APP_SECRET_KEY` (`component/SecretCipher`, 32 bajty w Base64, musi być stały). Bez tego klucza połączenia nie da się zapisać. Po zapisie od razu jest test logowania. Hasło nigdy nie wraca do przeglądarki. Połączenie musi być z firmą z NIP-u sklepu (pierwsze połączenie sklepu z innym NIP-em daje 400; wgranie certyfikatu uzupełnia brakujący NIP sklepu, a wymiana połączenia na inną firmę go zmienia; NIP-u połączonego sklepu nie zmienia się w Ustawieniach → Sklepy - 409). Gdy firma sklepu (po NIP-ie sklepu) jest już połączona w innym sklepie, do którego użytkownik ma dostęp (`companies` w ustawieniach; sklep bez NIP-u nic nie dostaje i nie podłączy się sam), osoba z EDIT podłącza sklep bez certyfikatu: `POST .../settings/connection/link` z `{nip}` kopiuje dane logowania (`KsefConnection.copyCredentials`) ze sklepu, do którego ma dostęp, i testuje logowanie. Jeden użytkownik może mieć sklepy kilku firm. W drugą stronę: połączony sklep podłącza naraz inne sklepy użytkownika do swojej firmy (karta „Inne sklepy tej firmy”, `POST .../settings/connection/share` z `{storeIds}`, EDIT, lista w `otherStores` ustawień: tylko sklepy z NIP-em tej firmy, `otherStoresWithoutNip` to podpowiedź o sklepach bez NIP-u): kopiuje dane logowania i wynik ostatniego testu bez osobnego logowania do KSeF, pomija sklepy już połączone z tą firmą, a sklep z innym NIP-em albo bez NIP-u daje 409.
- **Logowanie do KSeF 2.0** (`component/KsefClient`, `app.ksef.base-url`, domyślnie produkcja `https://api.ksef.mf.gov.pl/v2`): `/auth/challenge`, `AuthTokenRequest` (`http://ksef.mf.gov.pl/auth/token/2.0`, `certificateSubject`) podpisany XAdES-BES otaczającym (`component/KsefXadesSigner`, ECDSA-SHA256 dla klucza EC z KSeF, exc-c14n, `SigningTime` + `SigningCertificate`), `/auth/xades-signature`, czekanie na status 200, `/auth/token/redeem`. Token dostępu trzyma w pamięci `KsefSessionService`, dopóki jest ważny. Sprawdzone na środowisku testowym KSeF.
- **Pobieranie** (`KsefSyncService`): faktury zakupowe (`Subject2`), przyrostowo po dacie trwałego zapisu (`PermanentStorage`, `Asc`, `restrictToPermanentStorageHwmDate`), od `ksef_sync_states.sync_cursor` firmy, a za pierwszym razem od `app.ksef.sync-from` (2026-02-01). Okna mają do 90 dni (KSeF przyjmuje najwyżej 100), strony po 250, scalanie po numerze KSeF. Kolejna strona zaczyna się od daty trwałego zapisu ostatniej faktury (nie przez `pageOffset`, bo głębokie strony KSeF liczy coraz dłużej), a brak odpowiedzi albo 5xx (`KsefException.temporary()`) jest powtarzany do 3 razy; timeout odczytu 120 s. KSeF pozwala tylko na 16 zapytań o metadane na minutę i 20 na godzinę. Przy 429 postęp zostaje w kursorze, a komunikat mówi, kiedy ruszy reszta. Przycisk „Pobierz z KSeF” pobiera w tle (wirtualny wątek, jedno pobieranie na NIP naraz, wspólne dla sklepów firmy i harmonogramu, połączeniem sklepu, który kliknął): nagłówek (`GET`) ma `syncRunning`, `syncStartedAt` i `syncNewInvoices`, front odpytuje go co 3 s, odświeża listę, gdy przybywa faktur, i po końcu pokazuje wynik. Co `app.ksef.sync-interval` (30 min) pobieranie rusza samo raz dla każdej firmy (połączeniem z udanym testem) (`app.ksef.sync-enabled`, w testach wyłączone w `src/test/resources/config/application.properties`).
- **Limity KSeF** (produkcja, na parę NIP + IP, okna przesuwne): metadane 8/s, 16/min, 20/h; pobranie faktury 8/s, 16/min, 64/h; reszta 10/s, 30/min, 120/h. Przekroczenia KSeF karze coraz dłuższymi blokadami, więc każde zapytanie idzie przez `component/KsefRateLimiter` z zapasem (metadane 2/s, 10/min, 16/h; faktura 2/s, 10/min, 50/h; logowanie 1/s, 4/min, 15/h), liczonym po NIP-ie (sklepy jednej firmy dzielą limit). Krótkie okna przeczekuje (do ~1 min), wyczerpana godzina albo 429 z KSeF (blokada na cały NIP do końca `Retry-After`) kończy zapytanie od razu z czasem „spróbuj za … min”. Historia zapytań i blokad jest też w bazie (`ksef_api_calls`, `ksef_api_blocks`, `component/KsefRateHistory`, wpisy starsze niż 2 h są czyszczone): restart przy wdrożeniu jej nie zeruje, bo KSeF liczy zapytania dalej, a przekroczenie po restarcie kończyło się coraz dłuższymi blokadami. Godzina limitu metadanych to 16 stron po 250, czyli ok. 4 tys. faktur; większa zaległość schodzi w kolejnych pobraniach (co 30 min). W testach wyłączony (`app.ksef.rate-limit-enabled=false`), sprawdza go `KsefRateLimiterTests`.
- **Które faktury widzi sklep:** sklep bez IDWew - wszystkie faktury firmy. Sklep z IDWew (`ksef_internal_ids`, IDWew = NIP firmy + `-` + 5 cyfr, z Podmiotu 3 faktury, `ksef_invoice_internal_ids`) - ze swoimi IDWew i wszystkie bez IDWew, a filtr `internalId` zawęża: `OWN` (tylko z IDWew sklepu), konkretny IDWew, `NONE` (tylko bez IDWew). Faktury z cudzym IDWew są wtedy niewidoczne, także po id (`KsefInvoiceSearch.visibleInStore`). Ustawienia podpowiadają IDWew z pobranych faktur.
- **Pomijani dostawcy** (`ksef_skipped_suppliers`, po NIP): ich faktury znikają z listy, widać je po włączeniu „Pokaż pominiętych dostawców”. Dodaje się ich też z menu faktury.
- **Faktury korygowane** (V45: `ksef_invoice_corrected`, `ksef_invoices.corrected_read_at/corrected_error`; `service/KsefCorrectedInvoiceService`, `KsefInvoiceReader.correctedInvoices`): metadane KSeF nie mówią, co koryguje korekta, więc co `app.ksef.corrections-interval` (10 min, w wirtualnym wątku, gdy `sync-enabled`) dla każdej firmy osobno: najpierw korekty z XML już w bazie (bez KSeF), potem pobiera XML korekt od najnowszej, tylko do `RESERVED_PER_HOUR` = 20 wolnych pobrań w godzinie limitu firmy (`KsefRateLimiter.remaining`), żeby zostały na „Pobierz PDF” i porównania. XML zostaje w `ksef_invoice_xml`. Pomija bazę (SCA PR Polska, NIP 7821977018, `IGNORED_SELLER_NIPS`: jej korekty wiąże się kwotowo) i dostawców pominiętych we wszystkich sklepach firmy. Limit albo chwilowy błąd KSeF przerywa przebieg (reszta w następnym), inny błąd albo nieczytelny XML zapisuje `corrected_error` i korekta nie jest pobierana ponownie. Lista faktur pokazuje przy korekcie „koryguje …” (`KsefInvoiceSummary.correctedInvoices`, `null` przed odczytem).
- **Wprowadzona:** numer faktury równy (bez względu na wielkość liter) numerowi dokumentu dostawcy w przyjęciu PZ, przypięty dokument albo ręczne oznaczenie (`ksef_invoice_entries`, da się cofnąć) **w którymkolwiek sklepie firmy**, czyli sklepie z połączeniem KSeF z tym samym NIP-em (`KsefConnectionRepository.findStoreIdsByNip`, w filtrze podzapytanie `companyStores` w `KsefInvoiceSearch`, w liście `KsefInvoiceService.summaries`). Ręczne oznaczenie i przypięty dokument cofa tylko sklep, który je zrobił. Dokument innego sklepu firmy lista pokazuje z nazwą sklepu i pobraniem bonu dostawy: `GET .../ksef/invoices/{id}/documents/{documentId}/delivery-note` (`KSEF_INVOICES:VIEW`, tylko przyjęcie PZ tej faktury w sklepie firmy, `KsefInvoiceService.companyDeliveryStore`), bez dostępu do samego sklepu.
- **Przypinanie dokumentów do faktur** (`document_ksef_invoices`, V23, `service/DocumentKsefLinkService`): przyjęcie PZ albo korekta od dostawcy (WZ, `DocumentType.canLinkKsefInvoice()`) przypięte ręcznie do faktury KSeF; odpięcie to znacznik. Przyjęcie PZ ma najwyżej jedną fakturę (przypiętą albo dopasowaną po numerze): druga daje 409, a podpowiedzi z faktury pomijają przyjęcia z inną fakturą; korekta WZ może mieć kilka. Z faktury: `GET .../ksef/invoices/{id}/documents/candidates`, `POST .../documents` z `documentId`, `DELETE .../documents/{documentId}` (KSEF_INVOICES:EDIT + DOCUMENTS:VIEW). Podpowiedzi: domyślnie kwota netto faktury vs wartość zakupu dokumentu ±10% (bez znaku, korekty bywają z minusem po jednej stronie), najpierw ten sam dostawca (kod dostawcy → NIP z listy dostawców = NIP sprzedawcy), potem najmniejsza różnica, max 30. Dokument pokazuje `ksefInvoices` (przypięte i dopasowane po numerze, `matchedByNumber`, tych nie da się odpiąć), lista PZ/WZ ma przy nr dok. dostawcy plakietkę faktury z pobraniem PDF i „Przypnij fakturę” bez otwierania dokumentu (`DocumentRowKsef`), a lista faktur kolumnę „Dokument” z `deliveries` (typ, link, `linked`). **Numer bonu** przyjęcia to numer wewnętrzny bez dwóch końcowych zer (999300 → bon 9993, `bonNumber` w `features/documents/format.ts`); pokazujemy go przy fakturach, pełny numer w podpowiedzi. Filtry listy: tekst (numer, dostawca, NIP, nr KSeF), daty wystawienia, status, rodzaj (faktury/korekty), IDWew albo „bez IDWew”, pominięci. Sortowanie i sumy netto/brutto liczą się w bazie. `KsefInvoiceService.list` i `ids` wyłączają JIT na transakcję (`KsefInvoiceRepository.disableJit`): podzapytania filtrów podnoszą koszt planu ponad próg JIT, a kompilacja to ok. 600 ms na każde z trzech zapytań listy przy ok. 13 ms samego zapytania.

Folder jest wspólny dla wszystkich plików PROTO (garmaż, przyjęcia MM, protokoły): `lib/proto-files.ts` (`useProtoFolder`, klucz przeglądarki `deli-order-proto` jak wcześniej), a ścieżka z ustawień to tylko podpowiedź (schowek) przy wyborze folderu, bo przeglądarka nie zapisze pod ścieżką podaną z kodu. Na tej samej stronie folder pliku nowych artykułów (CADBEZP, `productFileFolderPath`, puste = bez podpowiedzi), bo trafia do innego programu.
- **Protokoły z wprowadzania danych** (`ProtocolKind`: `LIQUIDATION` likwidacje = PROTO1, `STORE_NEEDS` potrzeby sklepu = 2, `ADVERTISING` reklama = 3, `DONATION` darowizna = 4, `REPRESENTATION` reprezentacja = 5, `TRANSFER` MM = 6; w nazwie zawsze numer własnego sklepu): `POST /api/stores/{storeId}/data-entry/protocols/{kind}` z `{lines:[{ean, quantity}]}` (`DATA_ENTRY:VIEW`, `DataEntryProtocolService`; ukryty protokół, kod niebędący EAN-em albo same zera = 400). Front: w pasku nad tabelą „Zmień znak” (+ ↔ − w zaznaczonych artykułach, bez zaznaczenia we wszystkich, bez kaucji i dostawy, toast „Przywróć”) i „Wygeneruj protokół” (`ProtocolDialog`: widoczne protokoły, plik do folderu plików PROTO, bez folderu pobranie; do pliku idą artykuły z EAN-em, nie zastępczym kodem z faktury, i ilością ≠ 0).

- **Plik zmian cen CTRLPRIX** (V65: `data_entry_price_control_files`, `dataentry/component/PriceControlFile`, `DataEntryPriceControlService`): przy zapisie pliku XML faktury (`XmlSaveDialog`) artykuły z kartoteki, których cena sprzedaży w tabeli różni się od ceny z chwili wczytania (`row.catalog.salePrice`: kartoteka albo promocja z kasy), idą do pliku `CTRLPRIX_RRRRMMDD_HHMMSS_<hasło dostawcy>_<login>.traite0` we własnym folderze przeglądarki (`usePriceChangeFolder`, klucz `data-entry-price-control`, podpowiedź jak folder PROTO). **PROTO i CTRLPRIX to nazwy wewnętrzne:** pracownik widzi w ustawieniach zapisu i komunikatach „Protokół” i „Zmiana cen” (hasło = `suppliers.keyword` z listy dostawców, np. GOBARTO; login osoby, która zapisuje, w pliku z programu sklepu jest tu `ImpEk`; program wczytuje tylko `.traite0`, a po wczytaniu sam zmienia końcówkę na `.Traite1`, 2, 3; V67 poprawiła nazwy w historii). Treść sprawdzona z plikiem z programu sklepu (33 znaki w linii, ASCII, CRLF). Linia: EAN na 13 znakach (krótszy dopełniony zerami, GTIN-14 z zerem jako EAN-13) i cena brutto w groszach na 20 cyfrach (7,99 = `00000000000000000799`), CRLF; kody zastępcze i cena 0 pomijane. `POST /api/stores/{storeId}/data-entry/export/price-control` z `{supplierId, sellerNip, invoiceNumber, rows:[{ean, salePrice}]}` (`DATA_ENTRY:VIEW`; dostawca wybrany w tabeli albo z listy po NIP-ie sprzedawcy, bez niego albo bez hasła 400) zapisuje plik od razu w historii i zwraca go z nagłówkiem `X-Supplier-Code`; `GET .../price-control-files` daje 10 ostatnich, `GET .../{id}/file` tę samą nazwę i treść (ustawienia zapisu: „Ostatnie pliki CTRLPRIX”, „Zapisz ponownie”). Sam plik, bez pliku XML: przycisk „Zmień ceny (N)” w przypiętym pasku (`savePriceControlFile` w `features/data-entry/price-control.ts`, wspólne z zapisem). Zapis kończy się jednym komunikatem „Zapisano pliki dla dostawcy <kod>” z listą plików (XML, CADBEZP, CTRLPRIX); błąd CADBEZP albo CTRLPRIX nie cofa pliku XML.

## Konwencje

- **Aktualność danych z raportów:** każdy import zapisuje datę wygenerowania raportu (`report_generated_at`). Raport jest aktualny tylko w dniu wygenerowania; inaczej pokazujemy „Nieaktualne · wymaga wgrania” (`components/ReportFreshness`, `lib/report-freshness.ts`).
- **Nic w aplikacji nie jest usuwane bezpowrotnie.** Usuwanie to znacznik (kiedy, kto), który da się cofnąć: toast z „Przywróć” od razu, a później z logów. Nowe funkcje projektujemy od razu tak; `repository.delete(...)` tylko dla danych technicznych (np. zużyte tokeny aktywacji).

- Komunikaty dla użytkownika (walidacja, błędy, UI) piszemy po polsku, kod i identyfikatory po angielsku.
- Ścieżki we froncie po polsku (`/ustawienia/role`, `/sprzedaz`), API po angielsku (`/api/settings/roles`).

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.
